## Outcome

CI-R08E deletes ordinary evidence already owned at a lower standard layer. It adds no dependency, script, checker, source assertion, executable inventory, route inventory, process framework, generic fixture, reporter, workflow, package command, or product behavior.

The built-runtime runner now starts one valid packaged server rather than a second all-disabled server followed by the main server. Focused module/service tests remain authoritative for disabled, incomplete, and ready semantics. The production-built Playwright journey at `/observability-client-test#token=disabled-token-must-not-be-sent` is the one retained packaged disabled-module representative. It proves the UI boundary returns its stable disabled response before auth or provider work and does not transmit the fragment. The encoded hostile-project runtime request remains separately because it catches packaged middleware registration, decoded-path classification, exact composed error headers, and write-before-rejection; it is not another module-state matrix.

Playwright remains the owner for production-rendered public runtime values, exclusion of build-only values, and exclusion of private runtime configuration. The runtime runner's duplicate homepage title, topbar, serialized-config, and private-value matrix is deleted. A differential fault found that the reduced Playwright fixture did not initially carry every runtime private canary: deliberately serializing the runtime Stripe secret passed all eight browser executions. The existing browser fixture and `assertRuntimePublicConfig` helper were therefore extended with the already-configured auth, disabled-provider Google, Stripe, and webhook values. Repeating the same fault then failed all four browser executions that inspect the runtime payload, and the existing output monitor also failed closed. This is a parity correction inside the selected Playwright owner, not a new scenario or framework.

The browser launcher still builds, migrates, starts one packaged server, waits for it to become live, and protects dynamic passwordless capture values across server output, Playwright output, and retained artifacts. Its startup liveness request is orchestration only. The duplicate browser build-output observer, build-database sentinel, and Playwright liveness response assertion are deleted; the runtime process owns build output/database secrecy, while focused health, one packaged transition, and the real container own health behavior.

The first hosted browser run exposed one lifecycle race in the retained real-login journey. Nuxt schedules its current app-manifest fetch after hydration; either of the journey's two deliberate hard navigations can cancel that non-navigation `fetch` with Chromium's `net::ERR_ABORTED`. The observer now derives the exact current-build manifest URL from evaluated Nuxt runtime behavior and classifies only that exact `GET`/`fetch` cancellation while one of those two `page.goto` calls is in flight. It does not ignore other URLs, methods, resource types, navigation requests, errors, or times. A controlled exact `aborted` fault passed; changing only the fault to `failed` remained fatal in both projects. Three clean restored runs then passed all eight executions without retry inside any run.

The runtime runner also deletes fixture-equality checks that merely compared objects assembled in the same file, two repeated whole-sandbox SQLite-family inventories, the historical `/api/health` absence probe, and helpers used only by those cases. It retains the exact post-build main/WAL/SHM sentinels. The deployment CLI remains under a separate same-held-connection SQLite `data_version` observer and local-object-directory fingerprint.

No guarantee is retired. The deleted evidence was either bookkeeping or a duplicate of the retained owners below.

## Official pinned basis

- Nuxt `4.4.8` documents that public runtime configuration is included in each page payload, private keys remain server-only, a built server does not read `.env`, and only matching `NUXT_` property paths override declared values at runtime: [pinned runtime-configuration guide](https://github.com/nuxt/nuxt/blob/v4.4.8/docs/3.guide/6.going-further/10.runtime-config.md). This supports assigning rendered public-versus-private behavior to Playwright while retaining process-only build and startup observations elsewhere.
- Nuxt `4.4.8` documents that the app manifest is enabled by default: [pinned experimental-features guide](https://github.com/nuxt/nuxt/blob/v4.4.8/docs/3.guide/6.going-further/1.experimental-features.md#appmanifest). Its pinned client payload plugin schedules `getAppManifest()` one second after the application is ready, and the composable fetches `/_nuxt/builds/meta/${buildId}.json`: [payload client source](https://github.com/nuxt/nuxt/blob/v4.4.8/packages/nuxt/src/app/plugins/payload.client.ts#L34-L45) and [manifest source](https://github.com/nuxt/nuxt/blob/v4.4.8/packages/nuxt/src/app/composables/manifest.ts#L24-L52). Nuxt also exposes `window.useNuxtApp` on the client and provides `$config` from the runtime payload: [pinned Nuxt-app source](https://github.com/nuxt/nuxt/blob/v4.4.8/packages/nuxt/src/app/nuxt.ts#L419-L430). The browser test therefore evaluates the installed runtime instead of parsing serialized config text. These sources explain why a later hard navigation can overlap the framework fetch; they do not justify ignoring unrelated request failures.
- Nuxt `4.4.8` documents that files in `server/middleware` are discovered and run before server routes: [pinned server-directory guide](https://github.com/nuxt/nuxt/blob/v4.4.8/docs/2.directory-structure/1.server.md). It does not promise application middleware filename order or percent-encoded path normalization. The one encoded packaged request therefore remains application evidence rather than being described as a Nuxt guarantee.
- Nuxt's pinned [error-handling guide](https://github.com/nuxt/nuxt/blob/v4.4.8/docs/1.getting-started/12.error-handling.md) describes server/API error rendering but does not promise this application's exact security headers. The exact `nitropack@2.13.4` publication commit shows current middleware scanning/order, production error defaults, and the outer Node listener: [scanner](https://github.com/nitrojs/nitro/blob/039b841669cd0641e54b443cba875b6552b24e05/src/core/scan.ts), [production error handler](https://github.com/nitrojs/nitro/blob/039b841669cd0641e54b443cba875b6552b24e05/src/runtime/internal/error/prod.ts), and [Node runtime](https://github.com/nitrojs/nitro/blob/039b841669cd0641e54b443cba875b6552b24e05/src/presets/node/runtime/node-server.ts). Those sources characterize the pinned implementation; the retained packaged canary owns the desired composed behavior.
- Playwright `1.61.1` documents that evaluation runs in the browser page context and awaits returned promises, while web assertions re-fetch and retry until their condition or timeout: [pinned evaluation guide](https://github.com/microsoft/playwright/blob/v1.61.1/docs/src/evaluating.md) and [pinned assertion guide](https://github.com/microsoft/playwright/blob/v1.61.1/docs/src/test-assertions-js.md). Playwright is consequently the appropriate existing owner for values actually serialized and rendered in the production browser boundary, but its deleted `/api/live` fetch did not catch a distinct browser failure.
- Playwright `1.61.1` emits `requestfailed` when a client cannot obtain an HTTP response and exposes the browser error through `request.failure()`: [pinned page-event contract](https://github.com/microsoft/playwright/blob/v1.61.1/docs/src/api/class-page.md#L505-L530). Its Chromium adapter forwards CDP's `errorText` into the request failure while separately retaining the protocol's canceled bit: [pinned Chromium network mapping](https://github.com/microsoft/playwright/blob/v1.61.1/packages/playwright-core/src/server/chromium/crNetworkManager.ts#L514-L548). Playwright's own pinned tests expect in-flight fetch cancellation on navigation and explicitly expect Chromium's interrupted navigation to report `net::ERR_ABORTED`: [fetch-cancellation test](https://github.com/microsoft/playwright/blob/v1.61.1/tests/library/trace-viewer.spec.ts#L633-L648) and [interrupted-navigation test](https://github.com/microsoft/playwright/blob/v1.61.1/tests/page/page-goto.spec.ts#L460-L477). The repository's exception is consequently bound to the exact request identity and intentional-navigation lifetime rather than to all aborted requests.
- Vitest `4.1.6` recommends testing observable inputs, outputs, errors, and side effects instead of implementation details, keeping tests focused on one behavior, and using real implementations where they are fast and controllable: [pinned testing guidance](https://github.com/vitest-dev/vitest/blob/v4.1.6/docs/guide/learn/testing-in-practice.md). This supports the focused module and health owners and deletion of fixture equality and inventories.
- Node 24 documents that a child's `close` event occurs after process exit and standard-stream closure, and that a detached POSIX child becomes a process-group/session leader: [child-process documentation](https://nodejs.org/download/release/latest-v24.x/docs/api/child_process.html). Node does not itself guarantee descendant cleanup. Repository helper behavior owns ordinary process-group and sandbox cleanup; CI-S02B/#70's retirement of actual-runner interruption evidence remains unchanged.
- SQLite documents that two [`PRAGMA data_version`](https://www.sqlite.org/pragma.html#pragma_data_version) readings are meaningful only on the same held connection, change for commits by another connection, and remain unchanged for that connection's own commits. The deployment observer follows that contract. It does not claim to detect reads, rolled-back writes, or arbitrary filesystem touches.
- Docker documents that a [`HEALTHCHECK`](https://docs.docker.com/reference/dockerfile/#healthcheck) exit code of `0` is healthy, `1` is unhealthy, and consecutive failures drive the container state. The real image/container transition therefore remains distinct from focused HTTP semantics; the browser liveness copy does not replace it.

## Rollback and residual risk

One ordinary code/documentation revert restores the second server and deleted duplicate assertions. It requires no schema, migration, provider, dependency, deployment, or product action.

Residual risk remains bounded:

- focused H3/Vitest behavior does not establish Nitro auto-registration or outer Node behavior, so one encoded packaged origin canary remains;
- one Playwright disabled-module route samples installed UI gating; focused tests own the exhaustive module/service matrix;
- Playwright inspects Nuxt's current serialized public payload plus rendered UI. The explicit private canaries cover configured sensitive classes, not every possible future private property; adding a private runtime key requires ordinary review of the existing boundary rather than a source inventory;
- the intentional-navigation classifier is coupled to Nuxt's evaluated runtime `buildId`, manifest path, Playwright request metadata, and Chromium error text. A future framework/browser change fails closed unless it still satisfies every exact predicate; broadening the exception requires new differential evidence;
- `data_version` observes commits made through another connection while the same observer remains open. It is not evidence that no read, rolled-back transaction, or filesystem metadata operation occurred;
- the container fault proves dependency-sensitive Docker health wiring, while focused tests own exact response/auth/redaction semantics; and
- actual-runner `SIGINT`/`SIGTERM` cleanup remains explicitly unclaimed. Ordinary success/failure cleanup and generic helper mechanics remain tested.

No guarantee is retired.
