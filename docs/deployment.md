# Deployment

> Imported donor history; this is not an operational WCU runbook. Follow current repository
> configuration and [`basic-release.md`](basic-release.md), which exclude OpenAI and user-file R2.

## Hosting Choice

The baseline production target is a Coolify-managed Docker application on a DigitalOcean Droplet. This keeps the first deployment understandable: one server, Git-based deploys, container logs, environment variable management, and an explicit persistent storage mount for SQLite.

## DigitalOcean Setup

1. Create a Droplet in the region closest to expected users.
2. Use SSH keys, not passwords.
3. Enable DigitalOcean monitoring and resource alerts.
4. Enable Droplet backups or document an equivalent backup plan before real users arrive.
5. Add block storage only if the database, local fallback objects, or backup strategy needs a separately managed volume.
6. Install Coolify using the current Coolify installation flow.

## Coolify App Setup

1. Create a normal Git-connected Docker Compose application from the root `docker-compose.yml` on the target server's **Standalone Docker (coolify)** destination. Leave **Connect to Predefined Network** off; Coolify's [Compose networking](https://coolify.io/docs/applications/build-packs/docker-compose#networking) already creates an isolated stack network and connects its proxy. Disable **Auto Deploy** and **Preview Deployments**, and do not start the resource yet.
2. Keep the committed single `build: .` and shared `${COMPOSE_PROJECT_NAME}_app:${SOURCE_COMMIT}` image configuration. Enable **Include Source Commit in Build** so Coolify supplies the commit-qualified tag to Compose, and disable **Inject Build Args to Dockerfile** so Coolify does not place that changing value ahead of expensive build layers. Coolify builds the image locally before it stops the old stack; this deployment does not require GHCR or a registry credential.
3. Assign the domain only to `web` and route it to container port `3000`; do not publish a host port.
4. Set the production domain.
5. Add the runtime `NUXT_*` and process controls from `.env.production.example`. Persistent baseline staging/production explicitly enables off-host backup by setting `COMPOSE_PROFILES=backup` for both build and runtime and supplying all five `BACKUP_R2_*` values as Runtime-only, Build-disabled values; forks that do not select backup omit the profile and values. When Observability source-map upload is enabled, make `NUXT_MODULES_OBSERVABILITY_ENABLED` available at both build and runtime, provide `SENTRY_AUTH_TOKEN` only as a Coolify Docker Build Secret, and provide `SENTRY_ORG`, `SENTRY_PROJECT`, optional `SENTRY_RELEASE`/`SENTRY_URL`, and an arbitrary `SENTRY_UPLOAD_CACHE_BUST` as non-secret build-only arguments. Change the discriminator whenever the upload credential, target, or intent changes.
6. Let the Compose application create its managed `app-data` volume at `/app/data`; record the UUID-prefixed Docker volume name that Coolify creates. Before the first deployment, inspect any volume declared by an earlier failed application. If it is absent or contains no valuable data, use the new managed volume; otherwise stop and design an explicit migration. Coolify also supports bind mounts, but the certified command examples below are intentionally for a named volume and must not be used unchanged for a bind mount.
7. Keep the Dockerfile health check enabled on `web`; it authenticates to container-local `/api/ready`. The one-shot `migrate`, worker, and enabled backup runner deliberately disable that HTTP check.
8. Keep the committed one-shot `migrate` service unchanged: it mounts the same volume, runs `node .output/server/maintenance.mjs migrate --confirm-app-stopped`, has `restart: "no"`, and gates every long-lived service through `service_completed_successfully`. A failed migration therefore leaves the application down.
9. The committed worker uses the same selected-commit image, named volume, and runtime environment as web, with init, unexpected-exit restart, and a `360s` stop grace. With Jobs enabled it starts through the Sentry preload; with Jobs disabled it skips that preload, stays inert without opening SQLite or initializing application providers, and exits cleanly on `SIGTERM`/`SIGINT`. Billing and every Files driver require Jobs plus this worker.
10. Off-host backup is the optional `backup` Compose profile. Its private runner uses the same selected-commit image and volume; exposes no port/domain; disables the web health check; validates all five backup-only values; and uses init plus an inert command for signal-safe Coolify Scheduled Tasks. Forks omit the profile and need no `BACKUP_R2_*` values. Persistent baseline staging/production enables it for both build and runtime.
11. Before certification, record that Coolify is the reviewed `v4.1.2` release, set the application-level stop grace period to `360` seconds, enable **Include Source Commit in Build**, disable **Inject Build Args to Dockerfile**, and leave **Raw Compose Deployment** and **Consistent Container Names** off. Leave the custom container/internal name and custom Compose build/start commands blank. Those settings keep deployment on Coolify's reviewed parser, the committed Sentry build-secret mount, a cache-preserving Dockerfile, all-container stop/remove, and ordinary `docker compose up -d` paths. Confirm the host Compose version and render the effective Compose configuration.
12. Certify staging before production: temporarily pause migration long enough to prove every old long-lived container is gone while only migration runs; then prove migration success starts every enabled dependent and a forced migration failure starts none. Persistent baseline staging must include the `backup` profile in this evidence. Remove both temporary probes afterward. Only then enable **Auto Deploy** for owner-approved `master` merges; keep previews disabled and suspend triggers during manual migration or restore.

## Runtime

The Docker image runs `node --import ./.output/server/sentry.server.config.mjs .output/server/index.mjs` from `/app` as `node:node` (UID/GID 1000 in the selected official Node 24 Bookworm Slim image). The same Dockerfile also packages the migration command, worker, and off-host backup operator; none installs pnpm, TSX, or raw source. The official Sentry preload applies to web and to an enabled Jobs worker; the disabled worker and operators skip that preload, and backup `validate-config` performs no provider work. Reviewed Coolify [`v4.1.2` injects the shared resource `.env` into every parsed service](https://github.com/coollabsio/coolify/blob/e7dff30b7c998c301fd91bd169727b90c59ec291/app/Jobs/ApplicationDeploymentJob.php#L677-L686) and [replaces literal empty service values with matching resource values](https://github.com/coollabsio/coolify/blob/v4.1.2/bootstrap/helpers/parsers.php#L1280-L1300). Compose therefore maps all five backup keys on migration, web, and worker through the reserved unset-or-empty `${BASELINE_BACKUP_ENV_EMPTY:-}` indirection, whose empty result [takes precedence even over an injected `env_file`](https://docs.docker.com/reference/compose-file/services/#env_file), while the enabled runner substitutes the configured values. Every enabled service resolves `NUXT_DATABASE_URL=file:/app/data/app.db` on the same local, same-host persistent volume. Production SQLite paths must be absolute `file:` URLs. Explicit local file objects derive their root from the database directory, so the production path is `/app/data/objects`; Nitro's local data is also below `/app/data`.

The `.dockerignore` begins with `**` and re-includes only the manifests, pinned bootstrap scripts, empty `.env.build`, and application sources needed for the production build. Docker documents that matching files are removed [before the context is sent to the builder](https://docs.docker.com/build/concepts/context/#dockerignore-files). The build has no credential `ARG` or `ENV`; the Sentry upload token exists only in the one BuildKit-secret-mounted build step. Docker's [`USER`](https://docs.docker.com/reference/dockerfile/#user) and [`COPY --chown`](https://docs.docker.com/reference/dockerfile/#copy---chown---chmod) mechanics establish the non-root final image; local container checks additionally verify the configured and effective UID/GID and prove a fresh named volume is writable without `chmod 777` or a root override.

[Nuxt documents](https://nuxt.com/docs/4.x/getting-started/deployment#nodejs-server) `.output/server/index.mjs` as the ready-to-run Node-server entry point. The build adds the bundled worker, bundled off-host backup operator, one maintenance script, committed SQL migrations, and the pinned Drizzle ORM migrator files to that standalone output. It does not ship pnpm, Drizzle Kit, TSX, tests, local data, repository metadata, or the raw application source tree in the final stage.

## Manual Versioned Image Maintenance Jobs

Normal Coolify releases use the committed `migrate` service before any long-lived service starts. Use this manual one-off procedure only for an operator-controlled recovery, restore, or exceptional maintenance window. Run the exact locally built image for the selected Git commit against the same persistent volume so maintenance cannot drift from the deployed application.

This recipe is specifically for a Coolify/Docker named volume. [Coolify documents](https://coolify.io/docs/knowledge-base/persistent-storage) that Docker Engine storage may instead be a bind mount; if staging selects a bind mount, record and use its exact host source rather than substituting `type=volume`.

Set shell variables to the currently running application container and the already-provisioned named volume, then derive its immutable local image ID. In one shell, inspect and retain the app's real mount before stopping it. Fail unless both Docker and the running app identify the same volume at `/app/data`; `set -euo pipefail` makes any failed precondition stop the recipe.

```bash
set -euo pipefail

APP_CONTAINER='replace-with-running-coolify-container'
DATA_VOLUME='replace-with-coolify-data-volume'
IMAGE="$(docker inspect --format '{{.Image}}' "$APP_CONTAINER")"

docker volume inspect "$DATA_VOLUME" >/dev/null
VERIFIED_DATA_MOUNT="$(docker inspect --format '{{range .Mounts}}{{if eq .Destination "/app/data"}}{{.Type}} {{.Name}} {{.Destination}}{{end}}{{end}}' "$APP_CONTAINER")"
test "$VERIFIED_DATA_MOUNT" = "volume $DATA_VOLUME /app/data"
```

Now temporarily suspend the approved `master` auto-deploy trigger and restart behavior, then stop the web, worker, migration, any enabled backup runner, and every other writer through the Coolify control plane. Keep the same shell open. Before migration, recheck the existing volume, require the recorded web container to be stopped if it still exists, and require no running container to use that volume. Only then assert that every writer is stopped:

```bash
set -euo pipefail

: "${IMAGE:?run the mount preflight first}"
: "${APP_CONTAINER:?run the mount preflight first}"
: "${DATA_VOLUME:?run the mount preflight first}"
: "${VERIFIED_DATA_MOUNT:?run the mount preflight first}"
docker volume inspect "$DATA_VOLUME" >/dev/null
test "$VERIFIED_DATA_MOUNT" = "volume $DATA_VOLUME /app/data"
if docker inspect "$APP_CONTAINER" >/dev/null 2>&1; then
  test "$(docker inspect --format '{{.State.Running}}' "$APP_CONTAINER")" = 'false'
fi
RUNNING_VOLUME_CONTAINERS="$(docker ps --quiet --filter "volume=$DATA_VOLUME")"
test -z "$RUNNING_VOLUME_CONTAINERS"

docker run --rm \
  --network none \
  --no-healthcheck \
  --mount "type=volume,source=$DATA_VOLUME,target=/app/data" \
  --env NUXT_DATABASE_URL=file:/app/data/app.db \
  "$IMAGE" node .output/server/maintenance.mjs migrate \
  --confirm-app-stopped

docker run --rm \
  --network none \
  --no-healthcheck \
  --mount "type=volume,source=$DATA_VOLUME,target=/app/data" \
  --env NUXT_DATABASE_URL=file:/app/data/app.db \
  "$IMAGE" node .output/server/maintenance.mjs backup \
  --output /app/data/backups/manual-YYYY-MM-DDTHH-MM-SS.db

docker run --rm \
  --network none \
  --no-healthcheck \
  --mount "type=volume,source=$DATA_VOLUME,target=/app/data" \
  --env NUXT_DATABASE_URL=file:/app/data/app.db \
  "$IMAGE" node .output/server/maintenance.mjs verify
```

The manual network-disabled backup above is a same-volume release safeguard, not the optional routine off-host policy. When the `backup` profile is selected, routine snapshots use its separately credentialed private runner and bundled `off-host-backup.mjs` command while web/worker may remain active; the operator verifies the copied database, conditionally writes a private immutable R2 object, and reads every byte back for SHA-256 verification. See [the backup runbook](../ops/backup-runbook.md) and [ADR 0016](adr/0016-private-r2-sqlite-backups.md). Persistent baseline staging enables the profile under #36; #37 creates and configures the real scheduled task and notifications, then executes and certifies provider behavior.

The supported package has exactly four entries. Generated `0000_pre_release_baseline.sql` and custom `0001_runtime_invariants.sql` retain their original hashes and create the prior complete relational baseline plus 16 authority triggers. Generated forward migration `0002_stripe_subscription_persistence.sql` preserves and extends Stripe rows for catalog, transition, dunning, Family join, and deletion-cancellation state; it moves an open legacy Checkout to reconciliation and a nonterminal legacy Family subscription with no cadence to `legacy_family_cadence_unknown` rather than inventing cadence. Custom `0003_stripe_subscription_invariants.sql` restores the six authority triggers intentionally dropped around table rebuilds and adds reservation/correlation guards, leaving exactly 30 triggers. Verification requires the exact four-entry ledger; all 30 triggers; the original `member_one_external_family_uidx` and `billing_checkout_attempts_one_open_uidx`; one-open-transition-per-organization, one-open-Family-join-per-recipient, unique deletion-request user/organization/subscription, unique subscription-item/grace-invoice, and accepted-plus-pending-unexpired capacity invariants. The schema has no Search or FTS objects. `migrate` requires the explicit stopped-app assertion, verifies that any existing ledger is an exact packaged prefix before applying SQL, then requires final hashes/timestamps and the complete schema to match the package. It uses the pinned [`drizzle-orm` `0.45.2` better-sqlite3 wrapper](https://github.com/drizzle-team/drizzle-orm/blob/273c78071d4841b497f5144734b38294df7ec64b/drizzle-orm/src/better-sqlite3/migrator.ts) and [SQLite dialect transaction](https://github.com/drizzle-team/drizzle-orm/blob/273c78071d4841b497f5144734b38294df7ec64b/drizzle-orm/src/sqlite-core/dialect.ts). When a recognized database already exists for a forward migration, migration first creates a timestamped verified snapshot under `/app/data/backups`. `backup` uses the pinned [`better-sqlite3` online backup API](https://github.com/WiseLibs/better-sqlite3/blob/v12.10.0/docs/api.md#backupdestination-options---promise), which maps to SQLite's [Online Backup API](https://www.sqlite.org/backup.html). Every migration, backup, and restored candidate must return exactly `ok` from [`integrity_check`](https://www.sqlite.org/pragma.html#pragma_integrity_check) and zero rows from [`foreign_key_check`](https://www.sqlite.org/pragma.html#pragma_foreign_key_check); SQLite explicitly says the first check does not detect foreign-key violations. [ADR 0015](adr/0015-final-pre-release-database-rebaseline.md) records the starting baseline and permanent forward-only boundary; #169 owns the two new forward entries, while ADRs 0010 through 0014 retain the Search, Files, AI, File Search, and Web Search product decisions.

Pinned Drizzle `0.45.2` creates `__drizzle_migrations` before it begins the transaction containing migration SQL and ledger inserts. A failed first-ever migration can therefore leave an empty ledger table even though application-schema changes rolled back. That state remains fail-closed: do not automatically delete or adopt a database merely because its ledger is empty. Because this repository is an unused baseline, reset only after confirming that no migration completed and no account or application data exists, with every writer stopped, and discard the database plus all three sidecar types together. Migration seeds no account or application data. Every later schema change preserves initialized data through a forward migration and corrected retry.

For a normal Git-connected Compose release on reviewed Coolify `v4.1.2`, Coolify [builds the selected commit before stopping the old application](https://github.com/coollabsio/coolify/blob/e7dff30b7c998c301fd91bd169727b90c59ec291/app/Jobs/ApplicationDeploymentJob.php#L707-L783), then runs ordinary [`docker compose up -d`](https://github.com/coollabsio/coolify/blob/e7dff30b7c998c301fd91bd169727b90c59ec291/app/Jobs/ApplicationDeploymentJob.php#L802-L875). Docker's [`service_completed_successfully`](https://docs.docker.com/compose/how-tos/startup-order/) condition makes Compose wait for `migrate` to exit successfully before it starts web, worker, or an enabled backup runner. Coolify explicitly says [rolling updates are not supported for Docker Compose](https://coolify.io/docs/knowledge-base/rolling-updates), so this release has intentional migration downtime rather than old/new overlap. Exact `restart: "no"` also excludes the completed migration container from application health status in the reviewed [application Compose status path](https://github.com/coollabsio/coolify/blob/e7dff30b7c998c301fd91bd169727b90c59ec291/app/Traits/CalculatesExcludedStatus.php#L96-L144).

Coolify stops and removes labeled containers individually rather than running `compose down`, so it preserves the managed volume and stack network. Its stop/remove commands ignore individual Docker errors; staging must therefore prove that the old writers are absent while migration runs and that a failed migration leaves every dependent stopped. This proof also depends on the default parsed-Compose and all-container paths: Raw Compose Deployment and Consistent Container Names must stay off, custom container/internal names blank, and custom Compose build/start commands unset. The approved [Auto Deploy](https://coolify.io/docs/applications/ci-cd/github/auto-deploy) trigger accepts only owner-approved merges to `master` after that certification. Suspend it during manual migration or restore. `/api/ready` checks the web process's current database and manifest availability; it does not establish migration-ledger identity, worker liveness, backup freshness, or cleanup progress and cannot replace the migration gate.

Docker's [`VOLUME`](https://docs.docker.com/reference/dockerfile/#volume) declaration identifies mutable image data, but [Docker volumes](https://docs.docker.com/engine/storage/volumes/) are chosen and persisted at container run time. Coolify must therefore mount a persistent resource explicitly at `/app/data`. Do not enable cleanup that can delete that volume. The local disposable-container check proves database rows, local-object bytes, backups, ownership, and readiness survive removal of one container and creation of another on the same fresh named volume; a real Coolify volume remains staging evidence.

For a direct Nuxt/Nitro deployment outside Docker:

```bash
npm run bootstrap
npm run pnpm -- run build
node --env-file=.env.production .output/server/maintenance.mjs migrate --confirm-app-stopped
node --env-file=.env.production scripts/run-pnpm.mjs start
```

Supervise exactly one `node --env-file=.env.production --import ./.output/server/worker-sentry.server.config.mjs .output/server/worker.mjs` as a second long-lived process after migration. Its worker-specific preload initializes Sentry only when Jobs is enabled; otherwise the process remains inert. Restart it after unexpected exit, allow its documented graceful-shutdown window, and alert on due-job backlog plus missed subscription-effect deadlines rather than process state alone. The direct deployment must run the packaged maintenance command successfully while web, worker, and every other writer are stopped, with automatic restarts suppressed, before it starts either process. All commands must load the same complete environment; merely copying `.env.production` does not make Nuxt load it in production. The ordinary root `start` command loads optional `.env`, not `.env.production`. The authenticated readiness endpoint remains web availability evidence and does not validate the ledger, worker operation, backlog, or deadlines.

## Environment

The required app core is `NUXT_DATABASE_URL`, private `NUXT_READINESS_TOKEN`, `NUXT_BETTER_AUTH_SECRET` (at least 32 characters after trimming surrounding whitespace), origin-only `NUXT_BETTER_AUTH_URL`, absolute and already-trimmed `NUXT_PUBLIC_APP_URL`, exact `NUXT_SOCIAL_PROVIDERS_GOOGLE_ENABLED=true|false`, and one complete core email transport. The readiness token is app-owned policy: it must start with an ASCII letter and contain at least 32 already-trimmed header-safe ASCII characters; production rejects the committed local sample. Generate it from a cryptographically secure random source and do not put it in public runtime config, URLs, build arguments, or logs. The auth URL must equal the app URL's origin. Production requires HTTPS except for explicit loopback test origins, and rejects the documented local auth secret plus known package/historical defaults. Startup does not attempt speculative entropy scoring. `NUXT_PUBLIC_APP_NAME` is optional and defaults to the literal `SmallWiseLabs Base App` when omitted; when supplied, it must be nonblank and already trimmed. `NODE_ENV`, `NITRO_HOST`, and `NITRO_PORT` are process controls; `NITRO_PRESET=node-server` is a build control.

Set only the documented `NUXT_` leaf variables. Aggregate object-node values such as `NUXT_BETTER_AUTH`, app-owned `NITRO_` aliases such as `NITRO_DATABASE_URL`, and `NITRO_ENV_EXPANSION` are unsupported and rejected before listen. The build pins Nitro expansion off. `NITRO_ENV_PREFIX` is inert because the compiled server's literal `NUXT_` prefix takes precedence, but it should not be used as application configuration.

Do not set Better Auth's alternate secret, origin, telemetry, test, or client-URL environment inputs. Runtime rejects `BETTER_AUTH_SECRETS`, `BETTER_AUTH_TRUSTED_ORIGINS`, `BETTER_AUTH_TELEMETRY`, `BETTER_AUTH_TELEMETRY_ENDPOINT`, `BETTER_AUTH_TELEMETRY_DEBUG`, `BETTER_AUTH_TELEMETRY_ID`, production `TEST`, `NEXT_PUBLIC_AUTH_URL`, `NEXTAUTH_URL`, and `VERCEL_URL`; builds also reject the final three client fallbacks. Rejecting `BETTER_AUTH_SECRETS` excludes Better Auth's ambient secret-rotation path; add and test one canonical versioned-secret interface before a fork relies on overlap rotation. The app uses a static canonical server origin, a relative same-origin client path, explicitly host-only cookies, ignores forwarded host/protocol values, and accepts only a single-valued `CF-Connecting-IP` for Better Auth rate-limit identity. Keep the Coolify origin inaccessible except through Cloudflare so clients cannot supply that trusted header directly, following Cloudflare's [origin-protection guidance](https://developers.cloudflare.com/fundamentals/security/protect-your-origin-server/) or an equivalent authenticated boundary.

Google is independent from the six optional feature modules. Exact false is the production-safe default and needs no client credentials. Exact true additionally requires already-trimmed `NUXT_SOCIAL_PROVIDERS_GOOGLE_CLIENT_ID` and nonblank private `NUXT_SOCIAL_PROVIDERS_GOOGLE_CLIENT_SECRET` before listen. Register the exact `https://<app-origin>/api/auth/callback/google` redirect on a Google OAuth web client. The app requests only `openid email`, uses the authorization-code flow with online access, and retains no provider tokens. Do not put either credential in Docker build arguments; do not expose the secret through `NUXT_PUBLIC_*`, logs, screenshots, or evidence files. Google documents exact redirect matching and authorization-code parameters in its official [web-server OAuth guide](https://developers.google.com/identity/protocols/oauth2/web-server), while the identity claims and minimum-scope behavior come from its [OpenID Connect guide](https://developers.google.com/identity/openid-connect/openid-connect).

Configuration-ready Google is not provider-certified. Keep the flag false for staging/production until R-033 records the real consent screen, callback and denial behavior, verified-email link/relink, account removal, and Google-side grant revocation. Local unlink deletes only the Better Auth account mapping; the app retains no token that could later be sent to Google's revocation endpoint, so it must not be presented as upstream revocation.

Every environment requires already-trimmed `NUXT_EMAIL_TRANSPORT=capture|smtp` and `NUXT_EMAIL_FROM`. Capture additionally requires `NUXT_EMAIL_CAPTURE_DIRECTORY`, resolved from the web server's working directory. It creates a private `0700` directory and atomically publishes `0600` JSON files containing the recipient and complete bearer authentication or invitation URL. Treat those files as credentials: keep them out of git, logs, support bundles, and shared artifacts, and remove them when no longer needed. Capture is for local test processes only. A production-mode test process may use exact `CI=true`; never set that process control on a deployed app, because production otherwise rejects capture before listen.

Deployed production uses `NUXT_EMAIL_TRANSPORT=smtp` and requires `NUXT_EMAIL_SMTP_HOST`, `NUXT_EMAIL_SMTP_PORT` (1–65535), exact `NUXT_EMAIL_SMTP_SECURITY=tls|starttls`, and nonblank `NUXT_EMAIL_SMTP_USERNAME` and `NUXT_EMAIL_SMTP_PASSWORD`. Username/password bytes are preserved; do not trim or log them. `tls` maps to TLS from connection start, while `starttls` requires the upgrade and fails instead of continuing unencrypted. Use a certificate-valid hostname because the application uses that same value for TLS SNI and does not expose a separate certificate server name for an IP endpoint. Nodemailer's official [SMTP options](https://nodemailer.com/smtp) define those transport semantics; its [message security options](https://nodemailer.com/message) support the file/URL-access restrictions enabled by this adapter.

Email startup completeness is configuration evidence, not provider availability. Neither synchronous startup validation nor protected readiness calls Nodemailer's networked `verify()` or sends a message. A resolved SMTP send proves transport acceptance, not inbox delivery. SMTP connection/authentication, sending-domain setup, real magic-link and invitation send/resend/inbox behavior, rejection, bounce/suppression, and provider operations remain R-033 staging evidence. Nuxt requires these nested private keys to be declared in `runtimeConfig` and overridden through matching `NUXT_` paths at server runtime; the built server does not implicitly read `.env`, as documented in [Nuxt runtime configuration](https://nuxt.com/docs/4.x/guide/going-further/runtime-config).

The same canonical `NUXT_PUBLIC_APP_URL` origin is the target for the app-owned command-origin middleware. Every unsafe app-owned `/api` request must present an exact `Origin`, `Sec-Fetch-Site: same-origin`, or a same-origin `Referer`; every supplied recognized signal must agree. Missing, malformed, `null`, cross-site, same-site, `none`, and conflicting signals return redacted `403 CROSS_ORIGIN_REQUEST_BLOCKED`. Do not configure the proxy to rewrite hostile browser `Origin`, `Referer`, or `Sec-Fetch-Site` values into trusted ones, and do not use inbound `Host`/forwarded-host values as an alternate application origin. A domain/origin change therefore requires an intentional `NUXT_PUBLIC_APP_URL` and `NUXT_BETTER_AUTH_URL` change plus the full auth, origin-policy, redirect, cookie, browser, and provider-callback test matrix.

The exact bypasses are independent authenticated boundaries, not deployment shortcuts: Better Auth owns `/api/auth/**` under its documented [CSRF/origin protections](https://better-auth.com/docs/reference/security); `POST /api/webhooks/stripe` requires Stripe's unmodified payload and official SDK signature verification according to [Stripe's webhook verification documentation](https://docs.stripe.com/webhooks/signature); and the two Observability test commands require their private token. Local `PUT /api/files/:id/content` is not a bypass: it requires same-origin evidence as well as the session, signed upload capability, and persisted-owner checks. R2 browser PUTs target Cloudflare's S3 API and require the exact-origin bucket CORS policy. No generic `Authorization` header bypass exists. These application choices follow the [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) and [Fetch Metadata specification](https://www.w3.org/TR/fetch-metadata/), but the stricter agreement/missing-header policy is owned by this baseline.

All six startup-completeness flags are required, with exact lowercase `true` or `false`: `NUXT_MODULES_BILLING_ENABLED`, `NUXT_MODULES_FILES_ENABLED`, `NUXT_MODULES_AI_ENABLED`, `NUXT_MODULES_TURNSTILE_ENABLED`, `NUXT_MODULES_OBSERVABILITY_ENABLED`, and `NUXT_MODULES_JOBS_ENABLED`.

When enabled, provider requirements are:

## Release Checks

Use `ops/deployment-checklist.md` for releases. The short version is: select Node 24, install with `npm run bootstrap`, run `npm run verify:pinned`, migrate staging first, back up production SQLite, deploy, smoke test, then check Sentry, Coolify logs, and DigitalOcean alerts.

Run `pnpm run ops:readiness:strict -- --env-file=.env.production` before production deploys to confirm the external service environment contract is configured. A passing result does not certify SMTP connectivity or message delivery.
Run `pnpm run ops:smoke -- --base-url=https://your-app.example.com` after deploys for a non-mutating public-liveness, app-shell, security-header and private-route boundary check. Its Billing probe is credential-free `GET /api/account/billing`; do not configure or monitor the retired `/api/billing` path. Do not send the readiness token to this public smoke command.

Browser command clients supply the protected request signals automatically. Any deliberately supported non-browser client calling an app-owned unsafe API must send a canonical `Origin` (or be designed and reviewed as a new exact capability boundary); a bare bearer credential does not bypass the policy. This is separate from public `ops:smoke`, which is read-only.

`GET /api/live` is public and returns an empty `204`; after startup, its app-owned request path bypasses runtime configuration and dependency checks. `GET /api/ready` requires `Authorization: Bearer <NUXT_READINESS_TOKEN>`, checks manifest health and SQLite through a fresh read-only connection, returns only `{"status":"ready"}` on success, and returns redacted `503 SERVICE_NOT_READY` on dependency failure. The Docker probe requires exact `200` and the exact ready body, so Docker marks the container unhealthy on `401`, `503`, malformed output, timeout, or network failure. These mechanics follow [Nuxt private runtime configuration](https://nuxt.com/docs/4.x/guide/going-further/runtime-config), [H3 response statuses](https://v1.h3.dev/utils/response), [Docker `HEALTHCHECK` exit semantics](https://docs.docker.com/reference/dockerfile/#healthcheck), and [Coolify Dockerfile health-check precedence](https://coolify.io/docs/knowledge-base/health-checks). Route names, token rules, response shapes, and the one-second SQLite probe timeout are explicit application policy from the canonical guide.
