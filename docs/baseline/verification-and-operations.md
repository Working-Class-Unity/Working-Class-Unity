# Verification and Operations Guide

Status: **approved canonical target as of 2026-07-09, amended through 2026-07-16 by ADR 0015 and by the current #169 subscription contract**. This guide defines evidence required for future repairs and forks. It does not claim external staging or provider certification that has not been performed.

## Evidence principle

Agent instructions are guidance; deterministic commands and observed runtime behavior are evidence. A change is not complete because files exist, types compile, or an agent says it looks correct.

Use these evidence labels in Issues/PRs:

- pass with exact command/count/result;
- fail with exact reproducible symptom;
- not applicable with reason;
- externally blocked with the missing environment/account named;
- residual risk with owner and follow-up.

## Toolchain contract

- Node `>=24.11.0 <25.0.0` is the single supported range. `.nvmrc` and every Docker stage select Node 24, while the root and application package engines and executable contract enforce Nuxt 4.5's minimum within that line.
- pnpm is pinned exactly to 11.1.2 in `packageManager` and package engines. `npm run bootstrap` and `npm run verify:pinned` use the repository runner to obtain that version through npm, so Corepack and a global pnpm installation are not prerequisites.
- Frozen lockfile installs are required for verification and release.
- Provide stable root scripts for format/check/test/build/integration/browser/Docker/readiness.
- Generated files and ignored runtime artifacts must not be required from the developer's dirty checkout.

## Verification model

### Local check

`pnpm run check` covers:

- formatting check;
- ESLint;
- Stylelint;
- TypeScript/Nuxt typecheck;
- targeted unit and route/integration tests for changed behavior;
- fresh migration/schema consistency when data code changes;
- dependency/secret/provenance policy.

The ordinary suite is behavioral, not a coverage-percentage exercise. Security,
family-plan authority, and private-resource boundaries remain in scope.

### Full local verification

`pnpm run verify` additionally covers:

- the network-backed supply-chain scan;
- production build;
- production Docker build;
- built-container runtime-config and readiness probes;
- isolated mutating API/provider-contract suite;
- scripted browser journey and automated accessibility scan;
- clean-baseline initialization and repeat idempotence; after this baseline, any future initialized-database upgrade must prove transactional rollback and corrected retry.

### Staging gate

Required before release/fork-ready evidence:

- exact `master` commit deployed to persistent `baseline-staging`;
- isolated provider sandboxes/resources and staging-only credentials;
- migration, persistent volume, backup, and isolated restore;
- Stripe checkout/success/cancel/failure/duplicate/out-of-order cases;
- R2 upload/download/integrity/CORS/cleanup;
- Turnstile action/hostname and failure behavior;
- direct OpenAI project/key/model, isolated deployment-owned File Search corpus, reviewed Web Search domain policy, runtime/operator permissions, combined tool ceiling, quota/idempotency/timeout/history/citations/delete, retention/HIPAA, billing, third-party behavior, and no-content logging settings;
- magic-link/social/email delivery and account linking;
- Sentry server/client events, scrubbed payloads, release/maps, alerts;
- target desktop/mobile responsive-browser behavior;
- read-only post-deploy smoke and observation window.

## App-command origin evidence

Every unsafe app-owned `/api` command is protected before handler/session/body work, except for exact method/path boundaries that authenticate an independent signature or capability. The policy accepts exact configured `Origin`, `Sec-Fetch-Site: same-origin`, or a same-origin `Referer` fallback; requires all supplied recognized signals to agree; and rejects missing, malformed, `null`, cross-site, same-site, direct-navigation (`none`), and conflicting signals with stable redacted `403 CROSS_ORIGIN_REQUEST_BLOCKED`. It compares against validated `NUXT_PUBLIC_APP_URL`, never inbound host/forwarded headers. These strict choices must be identified as application policy based on the [OWASP CSRF guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [MDN Fetch Metadata guidance](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Fetch_metadata), and the [W3C Fetch Metadata specification](https://www.w3.org/TR/fetch-metadata/).

Required evidence has distinct layers:

1. focused policy tests enumerate workspace, project, file, billing, and account-lifecycle command families; safe/non-API exclusions; missing/malformed/conflicting signals; and every exemption plus neighboring methods/paths;
2. middleware integration proves a hostile request gets the stable redacted code before the handler, and the numbered optional-module gate still returns `404 MODULE_DISABLED` first;
3. one built encoded-project canary rejects hostile origin with stable privacy/security headers and no database mutation; focused real-H3/service behavior owns the billing matrix, while one isolated packaged-app billing canary owns canonical `/api/webhooks/stripe` route/config mounting, Nitro raw-body composition, official SDK test-header verification, and duplicate receipt idempotency;
4. later route Issues supply full session/authorization/provider matrices rather than treating origin verification as authorization.

The exact exemptions are Better Auth `/api/auth/**` under its official [CSRF/origin contract](https://better-auth.com/docs/reference/security), Stripe `POST /api/webhooks/stripe` under [raw-body signature verification](https://docs.stripe.com/webhooks/signature), and private-token Observability test controls. Local `PUT /api/files/:id/content` remains origin-gated and independently requires its session and signed capability; R2 browser PUTs are provider requests governed by bucket CORS. There is no generic bearer-token bypass. Read-only workspace resolvers, user-owned project CRUD, Personal/Family billing, app-owned member self-leave, narrow manager removal, and account deletion exist. Project authorization remains an independent authenticated-user/resource predicate and never inherits family-plan membership.

## Optional-module contract tests

For every installed optional module, test:

1. disabled: no credentials/calls/UI promise, healthy status;
2. enabled with each partial credential combination: startup/readiness failure;
3. enabled with deterministic mock: success, provider error, timeout, malformed response, retry/idempotency;
4. staging sandbox: real happy path plus critical failure/recovery cases;
5. privacy: logs/Sentry/database/provider retention match the declared policy.

The canonical baseline certification runs the real staging-sandbox step for every provider-backed module at least once. A fork that keeps a module disabled retains its disabled/no-call and configuration tests but does not need that provider's sandbox account; this includes an unpaid fork with Billing disabled and no Stripe account or credentials. A fork must run sandbox evidence for every module it enables. Runtime providers are startup/readiness concerns, while local Jobs behavior is a schema/worker concern rather than a credential check. Billing and Files must both be incomplete when Jobs is disabled, and their ready states require one operational supervised worker from the web's immutable image against the same SQLite volume.

Billing account-deletion evidence must cover the exact fresh `{ "confirmation": "DELETE" }` boundary before provider work, durable cancellation intent before dispatch, immediate no-refund/no-proration cancellation, retrieval confirmation, and local deletion only after that confirmation. Timeout, connection loss, and ambiguous provider responses must retain the user and private state. Worker evidence must prove it can replay cancellation/retrieval but cannot call user deletion; a worker-confirmed cancellation still requires a later fresh exact `DELETE` from the person. Verify the Stripe Customer is not deleted and do not infer any of this from local signatures or an unperformed sandbox journey.

### Files evidence

Files needs behavioral evidence for all four configurations: disabled; enabled/incomplete; ready/local; and ready/R2 against deterministic exact-SDK transport fixtures. Files enabled while Jobs is disabled is incomplete. Disabled evidence observes no database, filesystem, queue, signing, SDK, or provider work.

Focused route/repository tests use at least two people in the same family-plan group. Every list, metadata-read, completion, download, and delete operation includes the session user in persisted predicates; bounded unknown values, deleted IDs, and foreign immutable IDs produce indistinguishable `404` responses and no provider capability or call. Overlong path parameters and malformed bodies or queries produce minimized `400` responses before provider work. DTOs omit owner/provider locators and internal lifecycle fields. Requests authenticate before validation or body/provider work.

Local upload evidence uses real streamed request bodies and temporary storage, not source-fragment assertions. It validates the declared 1-byte-through-25-MiB range and covers streamed declared/actual size mismatch, canonical base64 `Content-MD5`, media-type mismatch, expiry crossing before publication, pre/post-link authoritative checks, replay/no-overwrite behavior, interrupted temporary-file removal, restart persistence, path/symlink containment, concurrent account/file deletion, idempotent completion, and byte-for-byte owner download.

R2 contract evidence runs the exact `@aws-sdk/client-s3` and presigner versions against a deterministic request handler. It verifies Cloudflare endpoint validation, `region: "auto"`, `requestChecksumCalculation: "WHEN_REQUIRED"`, the absence of an automatic full-object CRC32 query, one exact persisted-and-signed 15-minute PUT/HEAD expiry, late/mismatched signer refusal, 60-second GET expiry, required signed PUT headers including attachment and private/no-store metadata, `If-None-Match: *`, server-trusted HEAD length/media type, three-attempt standard retries, 30-second abort, provider/signer-error normalization, and no secret/key leakage. Tests pass `ListObjectsV2` continuation tokens unchanged, bound adapter pages and deletes to 100, reject missing-key, oversized, or duplicate provider pages, inspect partial multi-delete failure, and prove restart-safe cleanup/provider-outage retry. The worker requests at most five objects and performs at most one list plus five sequential 30-second deletions, giving provider work a three-minute ceiling below the nonrenewed five-minute lease.

Current-schema evidence starts from an empty database and verifies Files constraints, indexes, integrity, and foreign keys. The mutating packaged smoke uses local storage only and owns create/upload/complete/list/read/download/delete plus same-family concealment; it never sends provider credentials or charges R2.

Real R2 evidence remains #37: bucket-scoped token, jurisdiction endpoint, deployed exact-origin CORS, browser PUT/HEAD/GET, integrity rejection, conditional replay, expiry, strong-consistency observation, pagination, transient/permanent error presentation, worker recovery, late-write cleanup, and account deletion. Local fakes and signing fixtures do not certify those external controls.

### AI evidence

AI needs behavioral evidence for disabled, enabled/incomplete, and ready states. Disabled route/service/worker evidence uses no OpenAI key and observes no AI database access, SDK construction, fetch, quota, or provider work. The common migration package still creates the optional tables, and account deletion unconditionally removes retained local AI rows without constructing a client or contacting OpenAI. Subordinate `NUXT_OPENAI_FILE_SEARCH_ENABLED` and `NUXT_OPENAI_WEB_SEARCH_ENABLED` switches default to exact false; either true while AI is disabled is invalid. Enabled-incomplete startup fails safely for every missing/invalid private key, project, exact model, subordinate switch, File Search vector-store ID, and Web Search one-through-100-domain policy. Domain tests reject schemes, paths, ports, credentials, wildcards, IP literals, whitespace, trailing dots, malformed labels, duplicates, redundant parent/subdomain entries, and caller overrides. Ready/readiness validates configuration and current SQLite availability only and must never retrieve a store, list files, search files/the web, validate live domains, or make another charged/provider probe.

Focused route/repository tests use anonymous, owner, foreign, and same-family non-owner callers. They prove authentication before parsing/provider work; immutable conversation-ID plus persisted-owner predicates; concealed unknown/foreign/deleted `404`; entitlement required for create/generate only when Billing is ready; existing-history access after entitlement loss; minimized DTOs; bounded cursor pages; 100 conversations; 32,000-byte messages; 200,000-byte rendered input; 4,096 output tokens; 50 reserved generation attempts per UTC day; one active generation through the transient per-owner lease; and clear/delete/account deletion including citation cascade, late-result rejection, and the intended lease/daily-bucket retention. Family membership never grants conversation or citation access.

Provider-contract tests run exact `openai@6.47.0` through injected deterministic fakes and never use a credential or network. They verify the fixed direct Responses endpoint/project/model; `store: false`; `background: false`; truncation disabled; explicit cache mode with no breakpoint/key; no provider Conversation, previous response, metadata, attachment, or streaming; low reasoning; server HMAC safety identifier; internal attempt `X-Client-Request-Id`; 60-second timeout/abort; `maxRetries: 0`; `logLevel: off`; safe text/refusal/model/request-ID/numeric-usage extraction; malformed/non-completed output rejection; and finite error normalization without exposing, persisting, or logging a raw envelope. Both searches false must serialize no tools, tool choice, parallel/max-tool controls, vector-store/domain values, or included results. File Search adds exactly `{ type: "file_search", vector_store_ids: [configuredId], max_num_results: 10 }`. Web Search adds exactly `{ type: "web_search", filters: { allowed_domains: configuredDomains }, search_context_size: "medium" }` without user location, source/result inclusion, blocked domains, image search, unsupported live-access field, or unlimited result budget. File-only, Web-only, and combined requests fix `tool_choice: "auto"`, `parallel_tool_calls: false`, and `max_tool_calls: 1`.

Output tests accept automatic zero-search/zero-citation responses and at most one completed built-in call total. They normalize at most ten ordered unique File citations to public/durable `{ type: "file", title }` and at most 20 ordered Web citations to `{ type: "web", title, url, startIndex, endIndex }`. Web tests require one completed output-text part, canonical HTTPS without credentials/nondefault ports, allowed root/subdomain hosts, bounded safe titles/URLs, valid text spans, exact-duplicate URL/span removal, and retained distinct spans. They reject nonterminal/extra/disabled tool calls, searched text without citations, mismatched citation kinds, foreign/malformed URLs, malformed/conflicting identities/titles/spans, multipart cited output, and over-limit sources. Provider IDs, vector-store IDs, queries, Web actions/complete sources, chunks, scores, attributes, tool-call IDs, included results, and raw envelopes never enter DTOs, SQLite, logs, or Sentry; citation URLs are never server-fetched.

Attempt tests prove one SQLite `IMMEDIATE` reservation, same-ID/same-content replay without another call, changed-content conflict, per-owner lease concurrency across clear/delete races, provider-dispatched quota non-refund, timeout/connection ambiguity retained as indeterminate without auto-resubmission, and conditional finalize against owner/conversation/history revision. Current-schema evidence checks both citation tables plus conversation/attempt/quota constraints, indexes, foreign keys, unrelated schema, and account-deletion cascades directly from generated `0000`. Account deletion removes conversations/messages/File/Web citations/attempts/generation leases/usage without an OpenAI call and never mutates the shared corpus.

Operator-contract tests invoke `pnpm openai:corpus prepare <manifest.json>`, `verify <vector-store-id>`, and confirmation-bound `delete` with separate operator configuration and deterministic SDK fakes. They cover a versioned contained regular non-symlink manifest, SHA-256 verification, at most 100 files, 50 MiB per file, 500 MiB total, a 30-minute indexing deadline, bounded pagination, zero retries, private receipts, compensation of known partial resources, explicit indeterminate-state failure, management-marker verification, and incomplete deletion. Ordinary application routes have no corpus create/upload/list/mutate/delete capability. Blue/green replacement is explicit: prepare and verify a new store, configure/deploy/certify it, then explicitly delete the old store; tooling never edits environment files, deploys, mutates the active store in place, or deletes it automatically.

Real OpenAI evidence remains #37: isolated environment project and corpus, distinct least-privilege runtime/operator service-account keys, exact model/File/Web tool and citation acceptance, root/subdomain filtering and redirects, live-access default, queries/actions/Unicode/multipart offsets, combined automatic selection, request IDs, provider rate/quota/refusal/errors/pagination, timeout/ambiguous outcome, project spend/billing/alerts and actual File/Web/storage usage, API-versus-ChatGPT billing, provider dashboard/log/data-sharing settings, current default or approved ZDR/MAM and HIPAA/BAA posture, third-party disclosure, deployed application/Sentry content exclusion, key rotation, and clear/delete/account/corpus deletion including provider consistency. `store: false` is not Zero Data Retention and does not delete persistent Files/vector stores; those resource endpoints are not ZDR-eligible, and live Web Search is not HIPAA/BAA-covered. Deterministic local fakes make no provider call or charge and do not certify these external controls.

## SQLite deployment constraints

- One app replica on one host/persistent volume by default.
- Avoid shared network filesystems and overlapping rolling writers unless explicitly proven safe.
- Use WAL/foreign keys intentionally; configure busy/concurrency behavior and monitor disk/lock errors.
- App and exactly one supervised worker use the same immutable image, complete runtime environment, local same-host volume, and database contract; claims are atomic, leased, and token-fenced, while handlers remain replay-safe for at-least-once execution.
- Billing or Files requires Jobs whenever enabled and requires that operational worker. Supervision restarts unexpected exits outside maintenance, allows bounded graceful shutdown, and is deliberately suppressed during stop-first migration/restore. Monitor process exits/restarts, oldest-due backlog, pending cancellation age, and scheduled-effect deadlines. Web readiness does not claim worker liveness, heartbeat, backlog, deadlines, or cleanup progress.
- Database path must resolve identically for auth, app repositories, jobs, migrations, backup, and readiness.
- A replacement does not receive traffic until migrations and readiness succeed.

- `.dockerignore` excludes `.git`, `.dex`, all `.env*` except intentionally copied examples if needed, data/DB/backups, node/build outputs, logs, coverage, editor/OS files, and other local artifacts.
- Build-only secrets use secret mounts/control-plane injection and do not persist in layers.

- The final image includes the worker and its Sentry preload; Compose uses the preload only when Jobs is enabled. The worker disables the inherited web health check, uses init/process supervision with unexpected-exit restart, and receives a `360s` stop grace. Release evidence also covers disabled inert shutdown, enabled graceful shutdown, restart after failure, backlog/deadline alerts, and restart suppression during stop-first maintenance.
- Provide a tested migration/maintenance image or one-shot job containing manifests, migrations, and backup/restore tooling.
- Persist DB and explicit local object fallback under `/app/data`.
- Prove synthetic canaries at both a context root and an allowlisted nested path do not cross `COPY`, then inspect final image configuration/history. Any stronger cache/layer absence claim must parse the actual stored layer contents; searching an outer saved-image byte stream is not sufficient evidence.
- Health probes use the intended liveness/readiness semantics, not HTTP 200 alone.

## Smoke tests

### Production-safe smoke

Read-only only:

- public shell and effective module-owned security headers, including the enforced CSP;
- public liveness; readiness only through the deployment platform's internal network probe or a short-lived authorized staff control, without exposing topology publicly;
- anonymous boundary on representative private routes;
- authenticated read-only journey using a designated synthetic staging account when appropriate;
- no user/project/file/billing/provider mutation.

The executable `ops:smoke` boundary is the only smoke that accepts a deployment URL. It sends credential-free `GET` requests and uses `/api/baseline` to derive enabled/disabled expectations; the Billing probe is `GET /api/account/billing`, not the retired `/api/billing` route. The built-runtime worker opens one read-only SQLite observer before the smoke and requires [`PRAGMA data_version`](https://www.sqlite.org/pragma.html#pragma_data_version) plus the local-provider-directory fingerprint to remain unchanged afterward.

### Mutating integration smoke

`api:smoke` accepts no target argument, refuses ambient app/provider variables before creating state, and builds, migrates, and starts the production app only on loopback. Every run owns a fresh named temporary SQLite database, runtime working directory, local Files state, and one locally signed Stripe packaging canary. “Runtime working directory” is filesystem/process state, not an app-owned workspace. The suite exercises representative identity, family-plan, project, local Files, and Stripe packaging behavior, then removes all owned state on ordinary success or failure using Node's documented [`mkdtemp`](https://nodejs.org/docs/latest-v24.x/api/fs.html#fsmkdtempsyncprefix-options) and recursive [`rm`](https://nodejs.org/docs/latest-v24.x/api/fs.html#fsrmsyncpath-options). The single billing check owns only canonical route/config/raw-body/official-signature composition and duplicate receipt idempotency; focused Vitest owns the billing behavior matrix. Real provider certification still runs separately in isolated persistent staging with provider sandboxes; the local Stripe signature fixture is not [Stripe sandbox](https://docs.stripe.com/sandboxes) certification.

## Backup and restore

When off-host backup is selected, define:

- schedule, freshness incident threshold, retention, and expected data-loss exposure without promising an RPO or RTO;
- encrypted off-host destination;
- private off-host key/SHA-256 receipt retention plus a dead-man monitor whose scheduler and state do not share the application/Coolify host;
- database/WAL-safe backup mechanism;
- object/metadata consistency window;
- restore authorization and incident record;
- periodic isolated drill cadence.

An enabled-backup drill retrieves the exact immutable key/hash receipt from the private off-host record, restores into a new empty disposable volume or equivalent private replacement environment, applies required migrations, invalidates restored session/one-time-verification credentials, passes ledger/schema/integrity/foreign-key checks, and verifies fresh login, family-plan/project reads, file bytes/integrity, billing projection, and enabled module readiness. It never mounts the staging/production volume or exposes the replacement publicly. Record elapsed time and data-loss window as observations, not an SLA. A fork that omits the capability records that no repository off-host recovery path exists or documents its separately reviewed replacement.

- No live payment/provider credentials in PR previews.
- Coolify previews may be added later with scoped secrets and disposable data; they do not replace persistent staging.

## Agent workflow tools

### Baseline

- Dex for long-running internal task/dependency memory.
- ESLint/Stylelint/typecheck/tests/build/migrations as deterministic gates.
- Browser automation for visible UI, console, accessibility tree, keyboard/focus, and responsive behavior.
- Sentry for staging/production fact gathering once configured.
- Dependency and secret scanners through the local verification commands.

### Recommended after the core is stable

- codebase health/dead export/dependency/cycle/duplication analysis;
- CSS specificity/token analytics;
- Storybook or another component example catalog once shared components justify it;
- PR preview deployments with scoped secrets.

### Watchlist, not baseline dependencies

- experimental unified check runners;
- beta non-Chromium automation engines for nonvisual workloads;
- AI code-execution/tool-composition frameworks;
- Cloudflare management SDK in dedicated ops tooling.

Choose one tool per job and pin it only after a compatibility proof. Do not turn the baseline into a collection of overlapping agent tools.

## Completion record

A task result should answer:

- What behavior changed?
- Which risk/requirement does it close?
- What exact unit/route/browser/container/staging evidence passed, with counts?
- What migration/rollback was exercised?
- Which external checks remain and why?
- What residual risk remains?

“Should work,” “code complete,” and “tests added” are not completion evidence.
