# Architecture

The app is intentionally boring: one Nuxt 4 monolith at repository root, with server routes, local SQLite, and narrow service adapters.

For a diagram-first walkthrough of the processes, trust boundaries, data ownership, feature slices, and representative
runtime flows, see the [visual tour](visual-tour.md).

## Boundaries

- UI code lives in `app/`.
- API handlers live in `server/api/`.
- Database schema and connection code live in `server/db/`. Schema modules live under `server/db/schema/`, with `schema/index.ts` as the Drizzle source of truth for migrations and application imports.
- Vendor services live behind `server/services/`.
- Server-only request helpers live in `server/utils/`.
- Shared constants that are safe for client and server live in `shared/`.

Cloudflare R2 Files access is isolated to the storage adapter under `server/services/storage/`; the file service and routes never construct S3 commands or accept provider keys as authorization. A second operator-only adapter is bundled as `.output/server/off-host-backup.mjs` for private SQLite snapshots. It reads only `BACKUP_R2_*` when explicitly invoked, uses a separate bucket/credential, and is absent from Nuxt runtime config, routes, readiness, web, worker, and Files authorization. Compose gives non-runner services explicit empty values for those keys so Coolify's shared runtime `env_file` cannot leak their configured credential values into those processes. Direct OpenAI Responses calls are isolated to the thin server-only adapter at `server/services/ai/openai.ts`; AI routes and persistence never handle raw SDK envelopes. Optional File Search adds one server-configured read-only corpus and title-only citations; a separate local operator command owns provider Files/vector-store lifecycle, never HTTP routes or conversation authorization. Optional Web Search adds only a server-configured domain allowlist and bounded URL/span citations; it creates no application-owned provider object, and the application never fetches citation URLs. Transactional email is isolated to `server/services/email/index.ts`, where one application message contract selects either private local capture or authenticated SMTP without exposing Nodemailer to auth/UI callers. These boundaries keep deterministic local substitutes and vendor details out of pages and route handlers without introducing a generic multi-provider or agent/tool framework.

Runtime configuration is centralized in `server/utils/runtime.ts`, while `shared/modules.ts` is the authoritative optional-module inventory and `shared/auth-providers.ts` is the smaller social-provider inventory. A synchronous Nitro startup plugin validates exact path-derived `NUXT_*` variables—including one complete core email transport and the independent Google flag/credentials contract—before the server listens, then ordinary in-process app consumers share one deeply frozen process-wide config. Preloaded Sentry and standalone worker/Drizzle operations use the documented canonical environment boundary instead. Readiness, request gates, service guards, and tests derive from these manifests. Nuxt requires private runtime keys to be declared in `runtimeConfig` and overridden through matching `NUXT_` paths; a built server does not load `.env` implicitly, as documented in [Nuxt runtime configuration](https://nuxt.com/docs/4.x/guide/going-further/runtime-config).

After startup, public `GET /api/live` bypasses app runtime configuration and dependency checks and yields an empty, non-cacheable `204`. Protected `GET /api/ready` authenticates an exact Bearer credential from private `NUXT_READINESS_TOKEN` before dependency work. It compares fixed-length SHA-256 digests with Node's `timingSafeEqual`, evaluates only manifest-defined local module health, and opens a fresh read-only SQLite connection for `SELECT 1`; it never calls optional providers. That read-only query proves current database availability, not migration-ledger or schema identity: release orchestration must complete and verify the packaged maintenance job before the application starts. Responses are frozen application-owned shapes with no module names, paths, timing, credentials, or exception text. The Dockerfile accepts only exact `200 {"status":"ready"}` and converts every other result to exit `1`, which Docker defines as unhealthy. [Coolify documents](https://coolify.io/docs/knowledge-base/health-checks) that Dockerfile health checks take precedence over UI checks and that failed health removes a resource from Traefik routing. The token syntax, route names, response bodies, and timeout are baseline application policy; the mechanics follow [Nuxt private runtime config](https://nuxt.com/docs/4.x/guide/going-further/runtime-config), [Node 24 constant-time comparison](https://nodejs.org/docs/latest-v24.x/api/crypto.html#cryptotimingsafeequala-b), the pinned [`better-sqlite3` read-only API](https://github.com/WiseLibs/better-sqlite3/blob/v12.10.0/docs/api.md), and [Docker `HEALTHCHECK`](https://docs.docker.com/reference/dockerfile/#healthcheck).

The production boundary is one non-root final build. Docker removes every non-allowlisted path before sending the [build context](https://docs.docker.com/build/concepts/context/#dockerignore-files), and the local container-build check supplies secret-shaped negative canaries at both a root and allowlisted nested path. The final Nitro output contains the server, bundled worker, bundled off-host backup operator, `maintenance.mjs`, committed migrations, and the exact pinned Drizzle ORM migrator files; it does not require the workspace CLI at runtime. The current package has four entries: preserved baseline `0000`/`0001` plus #169's generated Stripe persistence `0002` and custom invariants `0003`, ending with exactly 30 triggers. Normal Coolify releases run the packaged migration through the committed one-shot service after the old Compose containers stop; manual backup, verification, or stopped-app restore runs the selected commit's local image without networking or its web health check against the exact `/app/data` volume. The maintenance entry validates absolute `file:` configuration; accepts backup/restore files only as regular, non-symlink direct children of `/app/data/backups`; uses SQLite's [Online Backup API](https://www.sqlite.org/backup.html); runs integrity plus foreign-key checks; and requires the applied migration hashes/timestamps and app-schema objects to match a packaged prefix before migration and the full package afterward. Missing, corrupt, wrong, or ambiguous initialized state fails closed without automatic adoption or deletion. Restore accepts only a compatible recognized package prefix, then validates, stages, migrates, invalidates restored sessions and one-time verification rows, checkpoints, and verifies the candidate before live replacement; the database and sidecars move together. Healthy live state receives a verified snapshot, while corrupt or otherwise recoverable prior state remains in a private quarantine after recovery; busy, locked, or inaccessible state fails closed. Every schema change uses a forward transactional migration that preserves initialized data and supports corrected retry. These same-build, stopped-writer, identity, path, backup, and swap rules are app-owned policy. The migration package follows Drizzle's documented [`generate`](https://orm.drizzle.team/docs/drizzle-kit-generate) and [custom migration](https://orm.drizzle.team/docs/kit-custom-migrations) mechanisms. Docker's [volume lifecycle](https://docs.docker.com/engine/storage/volumes/) and SQLite's [active-transaction backup/restore warning](https://www.sqlite.org/howtocorrupt.html#_backup_or_restore_while_a_transaction_is_active) provide the underlying mechanics. Runtime-only Coolify values must be Build-disabled. The approved #36 workflow uses the reviewed default parsed-Compose path—local build, stop/remove old containers, one-shot migration, then dependent startup—and enables auto-deploy only for owner-approved `master` merges after staging certification. Raw Compose Deployment remains off, and triggers remain suspended during manual migration or restore.

Billing and either Files driver require Jobs plus exactly one supervised worker alongside the single web replica. Web and worker run the same selected-commit image, receive the same application contract, and mount the same local same-host `/app/data` SQLite volume; the worker substitutes only its packaged command and has no HTTP health check. Supervision restarts unexpected exits and permits graceful shutdown, while stop-first manual migration/restore deliberately suppresses restarts until maintenance completes. Operations monitor process exits/restarts, oldest-due backlog, pending cancellation age, and scheduled-effect deadlines. Web readiness proves none of those worker properties.

Pinned `nuxt-security@2.6.0` owns the standard browser-security headers, enforced Content Security Policy, per-response nonces, emitted-asset SRI, and `X-Powered-By` removal. It is configured explicitly rather than through the module's broader defaults; the application rejects runtime environment attempts to replace the reviewed policy. The custom security-header middleware has been removed. The remaining numbered application middleware applies the optional-module boundary and then the app-command origin boundary. The module boundary replaces the per-request public module-state defaults with a safe projection from validated private flags and returns stable 404 `MODULE_DISABLED` responses for disabled exclusive API prefixes and exact UI routes before the origin gate or handlers can authenticate, parse bodies, render pages, or perform I/O. Page-level guards repeat the UI check for client-side navigation. Direct adapters, repositories, and workers retain their own guard because routes are not the only callers. Client code imports only the lean `shared/module-states.ts` helper, not the rich manifest. [Nuxt server middleware](https://nuxt.com/docs/4.x/directory-structure/server#server-middleware) runs before server routes. Nuxt does not document application server-middleware filename ordering as a public contract, so numbering remains an implementation convention while focused and built-runtime tests protect the meaningful order: a disabled module wins before the origin boundary, and a hostile origin wins before the route handler. Browser and deployment tests separately protect the module-owned headers and CSP. Nuxt also documents the relevant [runtime-config hydration](https://nuxt.com/docs/4.x/api/composables/use-runtime-config) and [shared-directory](https://nuxt.com/docs/4.x/directory-structure/shared) behavior. [ADR 0007](adr/0007-nuxt-security-ownership-and-csp.md) records the full security-capability ownership split.

The second application middleware is an application-owned, fail-closed policy for every unsafe method under `/api`, whether or not the current route already uses a cookie. It compares request signals with the exact origin of validated `NUXT_PUBLIC_APP_URL`; it never trusts `Host`, `X-Forwarded-Host`, or `X-Forwarded-Proto` to choose the target origin. An exact `Origin`, `Sec-Fetch-Site: same-origin`, or same-origin `Referer` fallback can verify the request, but every supplied recognized signal must agree. Missing, malformed, `null`, `cross-site`, `same-site`, `none`, and conflicting signals yield redacted `403 CROSS_ORIGIN_REQUEST_BLOCKED`; an unrecognized future `Sec-Fetch-Site` value is ignored only when `Origin` or `Referer` verifies independently. Protected responses use `Cache-Control: no-store` and also vary on `Origin` and `Sec-Fetch-Site`, following OWASP's cache-separation recommendation even though this baseline does not intentionally cache command responses. This deliberately conservative policy is informed by the [OWASP CSRF Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [MDN's Fetch Metadata guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Fetch_metadata), and the [W3C Fetch Metadata specification](https://www.w3.org/TR/fetch-metadata/); requiring every signal to agree, rejecting `same-site` and `none`, protecting future unsafe app routes before they become cookie-authenticated, and using the configured origin instead of inbound host headers are explicit application choices. The generic `nuxt-security` CORS, CSRF, rate-limit, request-size, XSS-body, and method-restriction middleware is disabled because it does not fully express these application and Better Auth guarantees.

Both global route gates classify the same decoded `event.path` that pinned H3 passes to its router and remove the query using the router's own first-`?` rule. They never classify the raw `originalUrl`: H3 routes `/%61pi/projects` as `/api/projects`, so raw-path classification would bypass both the module and origin boundaries. This exact compatibility behavior comes from pinned H3 `1.15.11` [app dispatch](https://github.com/h3js/h3/blob/v1.15.11/src/app.ts), [event path](https://github.com/h3js/h3/blob/v1.15.11/src/event/event.ts), and [router matching](https://github.com/h3js/h3/blob/v1.15.11/src/router.ts), not from a broad framework guarantee. Focused H3 regressions own fully and partially encoded API segments, exact exemptions and neighbors, module-before-origin ordering, and the case-sensitive `/API` control. One packaged `/%61pi/projects` canary separately proves that the built Nuxt/Nitro composition preserves decoded-path classification, origin-middleware registration, stable rejection with applicable JSON error headers, and no project write.

Exemptions are exact method/path capabilities, not a generic `Authorization` bypass. Better Auth owns `/api/auth/**` and retains its documented [CSRF, Fetch Metadata, and trusted-origin checks](https://better-auth.com/docs/reference/security). `POST /api/webhooks/stripe` instead authenticates the unmodified raw body through `stripe@22.3.1` signature verification, following [Stripe's webhook verification requirements](https://docs.stripe.com/webhooks/signature). `POST /api/observability/client-test` and `POST /api/observability/test-error` use their private operational token. Local `PUT /api/files/:id/content` remains origin-gated and then requires its session, short-lived upload capability, and persisted-owner checks; an R2 browser PUT targets Cloudflare's S3 API and relies on the bucket's exact-origin CORS policy rather than this application middleware. All neighboring methods and paths remain protected. These exemptions change only the browser-origin gate: their own signature/token, module, validation, and authorization boundaries remain mandatory. Focused real-H3 and service behavior owns exact-byte, invalid-signature/no-write, ordering, idempotency, and minimized projection guarantees; local fixtures do not certify Stripe sandbox or live delivery.

The app-owned [`error.vue`](https://github.com/nuxt/nuxt/blob/v4.5.0/docs/1.getting-started/12.error-handling.md) renders a single accessible main landmark, distinct non-sensitive 404/general-error titles, and a guarded `clearError({ redirect: '/' })` recovery action for both SSR and fatal client-navigation errors. Module-disabled errors retain their stable explanation and code. The page reads only the documented `NuxtError.data` field populated by [`createError`](https://nuxt.com/docs/4.x/api/utils/create-error); arbitrary error messages, causes, and stack data are not rendered, and there are no literal `/404` or `/error` application routes.

The per-request projection and current numbered middleware convention rely on exact pinned publication sources, not on a general Nuxt mutation guarantee. Nuxt's public runtime-config documentation describes server-side runtime config as read-only. npm registry publication metadata for `nitropack@2.13.4` identifies commit `039b841669cd0641e54b443cba875b6552b24e05`; its [runtime-config implementation](https://github.com/nitrojs/nitro/blob/039b841669cd0641e54b443cba875b6552b24e05/src/runtime/internal/config.ts) creates and event-caches a mutable request clone, and its [directory scanner](https://github.com/nitrojs/nitro/blob/039b841669cd0641e54b443cba875b6552b24e05/src/core/scan.ts) sorts discovered relative paths with `localeCompare`. Nuxt `4.5.0` tag commit `57614578c0102c16b69b64f1dac186c732856e90` then [builds the SSR context from `useRuntimeConfig(event)`](https://github.com/nuxt/nuxt/blob/57614578c0102c16b69b64f1dac186c732856e90/packages/nitro-server/src/runtime/utils/renderer/app.ts) and [exposes that context's public config to the client payload](https://github.com/nuxt/nuxt/blob/57614578c0102c16b69b64f1dac186c732856e90/packages/nuxt/src/app/nuxt.ts). Nitro's pinned [production error handler](https://github.com/nitrojs/nitro/blob/039b841669cd0641e54b443cba875b6552b24e05/src/runtime/internal/error/prod.ts) then replaces the baseline `Referrer-Policy` with the stricter `no-referrer` and adds its error-only `script-src 'none'; frame-ancestors 'none';` CSP. Packaged error evidence retains `nosniff`, `X-Frame-Options`, and production HSTS; it does not claim that browser-document-only COOP or Permissions Policy survives Nitro's JSON error path. Local verification protects externally meaningful behavior rather than source filenames or helper spelling; built/browser regression evidence must be rerun before any pin changes.

That pinned error-header behavior applies specifically to JSON error responses handled directly by Nitro's production error handler.

Standalone root operational scripts load optional root `.env` values through Node 24, while production build uses the assignment-free `.env.build` and static generation is unsupported.

Nuxt documents that its composables depend on Nuxt context and generally cannot be used by standalone code ([auto-import context](https://nuxt.com/docs/4.x/guide/concepts/auto-imports), [`useRuntimeConfig`](https://nuxt.com/docs/4.x/api/composables/use-runtime-config)). The single cached resolver therefore uses the actual `useRuntimeConfig` binding when Nuxt supplies it and the same environment evaluator only when that binding is absent. The worker calls the resolver before database/provider work; a present but broken Nuxt binding is not masked.

API routes validate request bodies and query strings with h3 validation helpers and Zod schemas before calling services. Structured error helpers in `server/utils/errors.ts` keep validation, auth, configuration, and provider failures consistent while redacting sensitive fields from exposed error data. Better Auth is mounted under `server/api/auth/[...all].ts`, configured server-side in `server/utils/auth/index.ts`, and private routes call `requireSession` before applying their data boundary. The server and Vue client enable the documented magic-link and Organization plugins. Verification is database-backed, the magic-link identifier is hashed, expiry is explicitly five minutes, and password UI/API is disabled. A request before hook requires and restricts the complete callback tuple before magic-link delivery/redemption or social state work and separately validates issuance origin. Because pinned `better-sqlite3` does not support async transaction functions and Better Auth runs database `after` hooks post-commit, custom baseline migration `0001_runtime_invariants.sql` provisions the personal organization and owner member in an SQLite `AFTER INSERT` user trigger. The one user statement commits or rolls back all three rows. Better Auth Organization remains an invisible family-plan membership authority; owner family-plan operations derive the marked organization and re-read persisted membership without trusting `activeOrganizationId`. The authenticated `/app` shell and private project routes do not carry organization scope and instead predicate private data directly on the authenticated user ID. Public workspace bootstrap and lookup routes are absent.

R-020A exposes separate app-owned `/login` and `/signup` intent pages through one shared passwordless/social component; pinned Better Auth may create an unknown user through either route, so neither page performs account discovery or claims existing-user-only enforcement. Successful normal authentication returns `/app`, invitation authentication preserves only an exact validated `/invite/:invitationId`, and errors return to the originating intent page. Authenticated `/account` owns minimized identity, linked-provider display/unlinking, pending family invitations, and immediate account deletion; R-021 moves the global sign-out command into the authenticated account menu. The frontend `/auth` route is absent, while the framework handler remains `/api/auth/**`, matching the separation in Better Auth's pinned [Nuxt integration](https://github.com/better-auth/better-auth/blob/v1.6.23/docs/content/docs/integrations/nuxt.mdx) and the automatic-account behavior in its pinned [magic-link guide](https://github.com/better-auth/better-auth/blob/v1.6.23/docs/content/docs/plugins/magic-link.mdx). `/` is a user-facing home, and `/legal/privacy` plus `/legal/terms` are fork-customizable disclosure templates rather than persisted consent or legal certification.

Google social identity is composed in `server/utils/auth/social.ts`. The provider is absent when its exact flag is false and startup rejects incomplete enabled credentials. Enabled authorization uses pinned Better Auth's Google authorization-code provider with database state, cookie validation, PKCE, online access, and exact `openid email` scopes; the app rejects caller-supplied scope, ID-token, return-path, and origin expansion before state work. Google documents that the email scope supplies `email` and `email_verified`, while profile claims such as `name` require the optional profile scope, so the app maps a missing name to the verified email rather than broadening permissions. See Google's official [OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) and [web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server) references plus the exact pinned [Better Auth Google source](https://github.com/better-auth/better-auth/blob/9dfceee14021fc15a2fb93023f39635f25b0b5ba/packages/core/src/social-providers/google.ts).

Implicit linking requires both the existing local user and the Google assertion to have verified the same email; no provider is trusted to bypass that check, different-email links are disabled, and explicit `/link-social` is absent. The database stores the provider/account identity and scope metadata but hooks null access, refresh, and ID tokens plus expiries on create/update. Token/profile-returning endpoints are absent and Better Auth logging drops provider payload arguments. Local unlink removes only the account mapping and allows magic-link recovery. Better Auth does not revoke Google grants on unlink, and this authentication-only design retains no token for later revocation; real Google removal/revocation remains R-033 rather than being inferred from local cleanup.

The canonical auth URL equals the app origin. Better Auth never derives it from forwarded host/protocol headers, and the app pins the Vue client to relative `/api/auth`. The session checks for `/login`, `/signup`, `/app`, and `/account` read Better Auth's public session endpoint through one shared literal-relative Nuxt `useFetch` request, so SSR forwards the incoming cookie and server/client hydration share one request key. The application projects only user ID, name, and email into that hydrated state; Better Auth organization identity, memberships, roles, capabilities, slugs, and `activeOrganizationId` are excluded. This narrow integration correction is required because pinned Better Auth `1.6.23` resolves the Vue `useSession(useFetch)` URL differently on the server and client; the resulting Nuxt payload-key mismatch is tracked in [Better Auth #5358](https://github.com/better-auth/better-auth/issues/5358). Production must first enforce the documented protected-origin boundary; only then does a Cloudflare-overwritten, single-valued `CF-Connecting-IP` identify both the global limiter and the plugin's separate five-request, 60-second request/redemption rules. Better Auth documents that `auth.api` calls bypass limiting, so focused evidence reaches the HTTP handler. That external proxy control is not locally certified. The one-replica limit is an inference from the pinned in-memory limiter's process-local storage; shared atomic storage must be selected and tested before scaling.

Magic-link single use is precise: pinned Better Auth consumes the verification value before user/session work, and the SQLite Drizzle adapter gates the winning row through one `DELETE ... RETURNING` operation. The same-process lock protects the surrounding latest-row selection and stale-row cleanup. This is not a transaction spanning verification consumption, user creation, and session creation; a downstream failure after consumption burns the link. See the pinned [`1.6.23` consumer](https://github.com/better-auth/better-auth/blob/9dfceee14021fc15a2fb93023f39635f25b0b5ba/packages/better-auth/src/db/internal-adapter.ts#L1229-L1382) and [Drizzle claim](https://github.com/better-auth/better-auth/blob/9dfceee14021fc15a2fb93023f39635f25b0b5ba/packages/drizzle-adapter/src/drizzle-adapter.ts#L978-L1028). The email adapter's local and deterministic SMTP tests prove only the application boundary. Startup/readiness does not connect to SMTP, and R-033 retains real hosted-delivery certification.

The custom origin boundary is not authorization. Read-only `GET /api/me` returns only the authenticated caller's minimized identity and safe module-state projection; public workspace bootstrap and lookup routes are absent. `/app` is the private personal shell and does not read or write a workspace selector. Better Auth invitation acceptance may write nullable `activeOrganizationId`, but application authorization ignores it. Invitation acceptance re-reads the exact persisted membership by immutable organization ID before returning `/app`, while invitation and billing management derive the authenticated user's uniquely marked organization and current persisted owner membership. Project handlers instead authenticate before parsing, derive `session.user.id`, and include it in every private-data predicate; same-plan membership never grants project access. Billing reads may inherit a granting entitlement from any one unambiguous joined family plan, but owner commands never trust session-selected organization state. `/account/billing` renders that role-oriented server projection without accepting or exposing provider or organization identifiers.

R-017I keeps Better Auth as the invitation-record state machine while replacing its broad native HTTP surface with bounded application routes. R-018A narrows manager operations to the marked organization's owner, accepts only an email for new invitations, hard-codes `member`, and returns fixed role-free invitation projections. #169 adds Stripe-current manager gates, seat reservations, a privacy-minimized accepted-member projection, and manager removal. The manager consumes one of six seats; each accepted member or pending unexpired invitation consumes one of the other five. If the original expiry passes during a valid recoverable `past_due` or `unpaid` Family episode, that pending invitation stays visible, cancelable, and seat-reserving until billing recovers or the Family lifecycle releases it; create/resend/accept remain closed and its timestamp is not extended. Web and worker serialize authoritative organization-scoped changes through SQLite transactions, compare-and-set revisions, and constraints rather than the older process-only lock. Create/resend/accept require active Family with renewal on and no grace, suspension, cancellation, downgrade, or reconciliation conflict. Cancel/decline/reject can release reservations while invitations are frozen. Accepted-member output contains only display name/email and an undisplayed opaque removal reference; the narrow removal command preserves identity/private data and restores unexpired residual Personal access. Better Auth's broad member-list and mutation routes remain disabled. Truthful email delivery, the application repair for Better Auth's pinned `transaction: false` partial acceptance, and remaining delivery/recovery limits are documented in the [canonical baseline contract](baseline/README.md).

R-018C exposes only `DELETE /api/account` for destructive lifecycle work, as amended by #169 for Stripe-backed owners. The command authenticates, accepts only exact `{ "confirmation": "DELETE" }`, and explicitly verifies a session younger than 24 hours before provider work. It durably records the exact-subscription cancellation request, sends immediate cancellation without automatic refund or proration, and retrieves the subscription from Stripe to confirm the result before local deletion. A timeout, connection failure, or unconfirmed result leaves the identity, credentials, organization, sessions, and private data intact. The existing at-least-once worker may retry cancellation and retrieval only; it can never call Better Auth deletion or interpret the queued request as continuing user consent. Even after worker confirmation, the person must return with another fresh session and exact `DELETE` confirmation.

After no Stripe cancellation is required or confirmed cancellation is durable, the command invokes the pinned Better Auth server API while its native deletion paths remain disabled. Better Auth's `beforeDelete` hook runs one synchronous SQLite transaction that writes only justified minimized provider continuity, removes the caller's current private/auth/family-plan state, clears surviving invitee session pointers, and deletes the user. The hook performs no Stripe, local-storage, R2, or OpenAI call. Invitees keep their identities and user-owned data. Identity-free continuity contains only provider/customer references, status/order timestamps, reconciliation purpose/policy, and optional purge time; raw webhook payloads, user/organization identity, Price, content, and credentials are never retained. Better Auth then expires the cookies; no `afterDelete` work can turn a committed deletion into an unretryable failure. The transaction commits empty delayed Files cleanup, and provider or worker failure may delay physical file-byte deletion without restoring application access. [ADR 0005](adr/0005-immediate-account-deletion-and-billing-detachment.md) records the account boundary, [ADR 0009](adr/0009-direct-stripe-family-plan-authority.md) records the billing refinement, and [ADR 0011](adr/0011-private-files-local-and-r2-lifecycle.md) records the completed Files lifecycle.

R-026 extends that same synchronous transaction to delete the caller's locally authoritative AI conversations, messages, File/Web citations, attempts, transient owner generation lease, and usage buckets. Runtime conversation handling creates no OpenAI Conversation, stored Response, file, vector store, or prompt object. The optional corpus is deployment-owned and created separately by an operator, not owned by any application user; Web Search creates no application-owned provider resource. Account deletion therefore performs no OpenAI call and cannot be delayed by a provider outage. A provider result arriving after the transaction cannot finalize because its owner/conversation/attempt authority no longer exists.

R-025/#32 implements Files as an optional private-resource vertical slice. The evaluator retains `disabled`, `incomplete`, and `ready`; `local` and `r2` are ready-state drivers. Files requires Jobs when enabled. Routes authenticate before validation/provider work, predicate every operation on immutable file ID plus the persisted session user ID, and conceal unknown/foreign/deleted resources as the same `404`. Family-plan membership and `activeOrganizationId` are irrelevant. Public DTOs omit owner and provider locators; new keys are opaque `files/v1/<file-id>` values and filenames remain display metadata only.

The database persists a singleton Files storage binding containing the selected driver and bucket identity plus the normalized account-and-jurisdiction endpoint for R2. File services and cleanup compare the active adapter with that binding and with each row's bucket before provider work; a mismatch fails closed without deleting metadata or bytes. Disabling Files does not rewrite the binding. Switching `local`/`r2` or selecting another R2 bucket, account, or jurisdiction requires an explicit stopped-writer data migration that inventories, copies, verifies, and cuts over the stored objects with a tested rollback. No such migration is included, so an initialized deployment must retain its bound provider identity.

Upload initiation records a 1-byte-through-25-MiB declared size, normalized media type, canonical base64 `Content-MD5`, and 15-minute expiry. Local upload validates the capability and live pending row before streaming to contained temporary storage, then rechecks the exact pending row/expiry immediately before hard-link publication and authoritative state before removing its authenticated crash marker. R2 uses the exact SDK and the row's signing instant to presign a conditional PUT and diagnostic HEAD with the same expiry; mismatched or already-expired signer output returns no capability. Server completion independently HEADs the object and idempotently changes pending to ready. Owner-scoped R2 downloads receive a 60-second GET capability, and signer failure is normalized. Presigned URLs are reusable bearer capabilities until expiry, so immediate metadata concealment has an explicit 60-second already-issued-download residual. The R2 adapter permits at most 100 objects per provider page, while each cleanup invocation requests and processes at most five, treats continuation tokens as opaque, rejects missing-key/oversized/duplicate pages, and precommits a phase-root successor before mutating cursor-bearing pages. Ordinary upload-expiry cleanup remains due at expiry plus one minute. After the singleton storage binding exists, the Files-ready worker runs a throttled SQLite `IMMEDIATE` check before each claim to maintain a viable full-root sweep on a 24-hour safety cadence. ## Data

SQLite is the first production database. Better Auth Organization owns the Drizzle `organization`, `member`, and `invitation` models. A nullable unique private `personal_owner_user_id` foreign key identifies each user's automatically provisioned family group without making mutable session selection authoritative. Preserved `0000_pre_release_baseline.sql` and `0001_runtime_invariants.sql` create the prior complete relational schema and authority triggers. Generated `0002_stripe_subscription_persistence.sql` adds the minimum plan/cadence, transition, dunning, Family join, residual Personal, and deletion-cancellation state while preserving recognized rows and moving ambiguous legacy live state to reconciliation. Custom `0003_stripe_subscription_invariants.sql` restores the six authority triggers dropped for table rebuilds and adds accepted-plus-pending-unexpired capacity and correlation guards. Final verification requires four ledger entries, exactly 30 triggers, one open transition per organization, one open Family join per recipient, unique deletion request per user/organization/subscription, unique Stripe subscription item and grace invoice, and the original family/billing indexes. The package has no application Search or FTS objects; future schema changes remain forward-only. The manager consumes one of six seats, while accepted members and pending invitations consume the other five under web/worker database authority; valid recoverable Family dunning temporarily preserves an expired pending reservation until recovery re-applies ordinary expiry. Projects, Files, and AI conversations are private and user-owned by immutable owner predicates; Family membership grants access to none. Better Auth's internal Organization slug remains opaque framework state, while projects use immutable IDs and no project slug. AI clear/conversation deletion retains minimized daily quota state plus a content-free active lease until matching finalization or expiry; account deletion removes both. Migrations seed no accounts or application data. Route handlers use repository functions under `server/db/repositories/` so database work stays server-only and out of page components. [ADR 0015](adr/0015-final-pre-release-database-rebaseline.md) records the preserved starting baseline; #169 adds the forward migration pair; ADRs 0010 through 0014 retain the Search, Files, direct OpenAI, File Search, and Web Search product decisions.
