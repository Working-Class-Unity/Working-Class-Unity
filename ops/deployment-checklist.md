# Deployment Checklist

## Before Deploy

- Confirm staging points at staging services and persistent storage.
- Select Node `>=24.11.0 <25.0.0` (`.nvmrc` selects the repository's major line).
- Run `npm run bootstrap`; this uses exact pnpm without requiring Corepack or a global install.
- Run `npm run verify:pinned`.
- Run `npm run pnpm -- run api:smoke`; it must create and remove its own loopback database, local provider fixtures, and runtime working directory without accepting deployment credentials or a target URL.
- Confirm the Git-connected Compose resource uses the target server's **Standalone Docker (coolify)** destination, declares no custom network, and keeps **Connect to Predefined Network** off so only Coolify's isolated stack network and proxy attachment apply.
- Confirm only migration retains `build: .`; migration, web, worker, and every enabled optional service use the same project-scoped `${COMPOSE_PROJECT_NAME}_app:${SOURCE_COMMIT}` image with local-only pull policy and no registry credential.
- Confirm the reviewed Coolify release is `v4.1.2`, **Include Source Commit in Build** is on, **Inject Build Args to Dockerfile** is off, the application stop grace is `360` seconds, Raw Compose Deployment and Consistent Container Names are off, custom container/internal names are blank, and custom Compose build/start commands are blank. Record the host `docker compose version` and rendered effective configuration.
- Confirm runtime-only values are Runtime-enabled and Build-disabled. If Observability is enabled, confirm the exact Observability flag is available at build and runtime, the Sentry token is a Docker Build Secret, the non-secret organization/project controls are build-only arguments, and the arbitrary cache discriminator changed for this upload credential/target. Confirm Preview Deployments remain disabled and Auto Deploy remains off until the staging migration-order certification passes; suspend it during manual migration or restore.
- Require exact private `NUXT_OPENAI_FILE_SEARCH_ENABLED=true|false` and `NUXT_OPENAI_WEB_SEARCH_ENABLED=true|false`. If AI is disabled, keep both false and confirm no OpenAI key, vector store, domain policy, SDK client, or provider call is required. If AI is deliberately enabled, require completed #37 evidence for the environment-specific OpenAI project/runtime service-account key, exact `gpt-5.6-luna` access, API billing/spend/rate controls, provider request/error/timeout behavior, dashboard retention/ZDR/MAM posture, and no prompt/response logging. File Search true additionally requires one private environment-owned vector store, title-only citation/storage/call/deletion evidence, and a separate corpus-operator key/project. Web Search true additionally requires one through 100 reviewed canonical domains, live root/subdomain/redirect/citation evidence, search cost/third-party/privacy evidence, and acknowledgement that live search is not HIPAA/BAA-covered. Keep all Nuxt OpenAI values Runtime-only and Build-disabled; never place operator credentials in application runtime.
- If Billing is enabled, require Jobs plus the restricted Stripe key, webhook secret, one Product with five distinct configured Prices (Personal weekly/monthly/annual and Family monthly/annual), and the explicit reviewed Portal configuration. Confirm the webhook destination uses only the documented 21-event target and Smart Retries uses eight attempts over no more than 14 days. Confirm all eight `NUXT_STRIPE_*` values are Runtime-only and Build-disabled. Do not treat local tests as Stripe sandbox evidence.
- For membership synchronization, follow [the Stripe synchronization runbook](stripe-membership-sync-runbook.md). Configure its separate read-only restricted key, exact `live|test` mode, and fixed grandfathering cutoff as Runtime-only/Build-disabled runner values; do not reuse the billing key. Require a recent verified backup, one redacted dry-run, measured duration and snapshot growth, sandbox permission/denial proof, one manual apply plus idempotent repeat, private task notifications, and the 26-hour independent freshness alert before enabling the daily task.
- Before production enablement, record the fork's reviewed detached-Stripe retention interval, the operator procedure that assigns `purge_after`, and a bounded drill that removes only due rows with no unresolved cancellation or reconciliation work. The baseline deliberately leaves `purge_after` unset rather than guessing this release/legal input.
- Record the selected Git commit, shared image reference, resulting local image ID for migration, web, worker, and every enabled optional service, and each service's actual `/app/data` mount type, Docker identity/source, and destination. Investigate any image-reference or image-ID mismatch because every enabled role must use the same selected-commit image and local same-host volume.
- Record whether off-host backup is selected. Forks may leave `COMPOSE_PROFILES` and all `BACKUP_R2_*` values unset; confirm no backup runner or task exists and record the accepted loss of the repository's off-host recovery path. Persistent baseline staging/production must set `COMPOSE_PROFILES=backup` for build and runtime, supply all five values Runtime-only and Build-disabled, and confirm one signal-safe private runner uses the selected image/volume with no ingress/HTTP health check. Record the `17 */6 * * *` target, 1800-second task timeout, success/failure notifications, 12-hour freshness alert, 30-day Bucket Lock, 35-day lifecycle, and monthly drill policy from [the backup runbook](backup-runbook.md).
- Confirm exactly one supervised worker uses the complete runtime environment, init, unexpected-exit restart, `360s` stop grace, and no inherited web health check. With Jobs enabled it starts through the Sentry preload; with Jobs disabled it skips that preload and remains stable and inert without SQLite/provider work. Billing or Files enabled requires Jobs and activates that worker.
- Confirm the volume is either truly fresh or has an exact packaged ledger prefix from the selected four-entry image. Verify the 30-trigger final schema and #169 transition/join/deletion/capacity invariants; any other populated or ambiguous state must fail closed without adoption.
- For a deliberately disposable pre-release database only, stop every app and writer, confirm there is no valuable user or application data, and remove the database plus its `-wal`, `-shm`, and `-journal` sidecars together before fresh initialization. A failed first-ever initialization additionally requires confirmation that no migration completed.
- Certify the default Coolify Compose lifecycle in staging before enabling Auto Deploy. Temporarily pause migration and prove every old long-lived container is absent, only migration is running, and no dependent has started. Let migration succeed and prove all long-lived services start. Force one migration failure and prove none starts. Remove both temporary probes and repeat a clean successful deployment.
- When off-host backup is selected for an existing initialized production volume, run `verify-latest --max-age-hours 12` as a metadata-freshness check and match it to the exact key/SHA-256 from the private off-host full-read receipt. Treat stale/missing metadata, a missing independent receipt, or a silent dead-man signal as an incident before migration. A truly fresh empty volume has no pre-existing receipt and follows the first-initialization branch below.
- For production, deploy the selected commit through the certified default Coolify path: build one image locally, stop/remove the old labeled Compose containers, run the one-shot migration, and start only enabled dependents from that image after its zero exit. A migration failure must leave the application down. When backup is selected, keep first-initialization traffic disabled until the private runner creates, fully reads back, and records the first off-host backup; for an existing volume, require the reviewed pre-migration receipt and successful migration before accepting traffic.
- When off-host backup is selected, confirm the selected backup can be located off-server, the exact receipt survives independently of the Coolify host, the dead-man monitor is healthy, and only explicit operator execution consumes the runner's backup credential.

## Deploy

- Deploy the selected Git commit through the committed Compose migration gate; never manually start web or worker around a failed gate.
- Confirm the container starts on port `3000`.
- Confirm the worker starts from the selected commit's local image and shared volume and stays supervised without an HTTP health check. Exercise graceful shutdown and one unexpected-exit restart. Record oldest-due backlog and deadline monitoring. For Billing-ready deployments, include pending cancellation age and scheduled subscription effects; for Files-ready deployments with an initialized storage binding, record that the pre-claim scheduler retains one viable full-root cleanup on its 24-hour safety cadence despite continuous or non-root/cursor work and that ordinary expiry-plus-one-minute jobs remain. Process start alone proves only liveness, not progress or convergence.
- If backup is selected, confirm the runner and six-hour Coolify task target are present without exposing a network service. If it is disabled, confirm both are absent. A merely running runner is not backup freshness evidence.
- Confirm `stripe-sync-runner` validates configuration and remains inert with no port or HTTP health check. Confirm the daily task targets only that runner and that migration, web, worker, and backup runner receive empty synchronization values.
- Confirm the configured and effective runtime UID/GID is `1000:1000` and the explicit persistent mount type, identity/source, and destination exactly match the preflight record at `/app/data`.
- Confirm public `/api/live` returns an empty `204`.
- Confirm Coolify reports the Dockerfile-authenticated `/api/ready` probe as healthy; do not expose its token through public smoke output. Readiness proves current configuration/SQLite availability, not ledger identity, OpenAI connectivity, vector-store existence, corpus search, worker health, or provider retention/deletion, and does not replace the pre-start maintenance gate or #37.
- Run `pnpm run ops:smoke -- --base-url=https://staging-or-production.example.com` for the credential-free `GET` deployed-app check.
- Never aim `api:smoke` at a deployed environment. It accepts no URL and owns its fresh loopback-only database, local provider fixtures, and cleanup.

## After Deploy

- On production, use only the read-only `ops:smoke` plus an approved designated-account read journey. Exercise login creation, file upload/download, billing, Stripe webhook delivery, direct OpenAI generation, and enabled File/Web Search only in isolated staging with provider sandboxes/projects, then record that evidence separately. Stripe staging must include exact fresh account deletion, durable cancellation intent, immediate no-refund/no-proration cancellation, retrieve/confirm-before-local-delete, ambiguous-outcome identity retention, worker cancellation-only retry, and fresh user reconfirmation after worker success. For File Search, verify the deployment-owned corpus, separate runtime/operator permissions, citations, cost, failure, replacement, and deletion. For Web Search, verify domain/root/subdomain/redirect behavior, live access, citations/offsets, cost, third-party/privacy posture, and combined File/Web automatic selection under #37. Never paste AI prompts/responses, search queries/actions, citation URLs/titles, provider identifiers, corpus contents, or operator receipts into evidence.
- Check Sentry for new client and server errors.
- Check Coolify web, worker, and private Stripe synchronization results plus oldest-due backlog, pending-cancellation age, scheduled-effect deadline alerts, and synchronization freshness without recording job payloads, raw errors, or user/object identifiers.
- Check DigitalOcean resource alerts.
- Fill a copy of `ops/production-evidence-template.md` with non-secret evidence from the deployed environment.
- Record the reviewer and review date on the filled evidence copy; this is a human staging review, not an executable Markdown contract.
- Record deployment notes: date, Git ref, database migration tag, operator, and any follow-up work.
