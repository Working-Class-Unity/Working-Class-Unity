# Production Operations

> Imported donor history; this is not an operational WCU runbook. Reconcile it with
> [`docs/basic-release.md`](../docs/basic-release.md) and current Compose before any deployment.

## Baseline

- Host the core app as a Coolify-managed Docker application on a DigitalOcean Droplet.
- Keep the production domain in Coolify and route DNS through Cloudflare.
- Mount persistent storage explicitly at `/app/data`; the Docker image uses `NUXT_DATABASE_URL=file:/app/data/app.db`, and explicit local object bytes resolve below `/app/data/objects`. The Dockerfile `VOLUME` declaration does not configure Coolify persistence by itself.
- Keep production SQLite out of the repository checkout and out of `.output`.
- Use the selected Git commit's packaged `node .output/server/maintenance.mjs` command for migration, verification, and stopped-writer restore against the inspected shared volume. Normal Coolify deployments run the committed one-shot migration service before any long-lived service; manual restore remains network-disabled. The SQLite Online Backup command may run while the app is active. The current package has exactly four entries: preserved baseline `0000`/`0001`, generated Stripe persistence `0002`, and custom Stripe invariants `0003`, ending with exactly 30 triggers. Require the exact ledger/schema; original family/billing indexes; one-open transition/join; unique deletion/subscription-item/grace-invoice; accepted-plus-pending-unexpired capacity; SQLite integrity/foreign keys; and no Search/FTS objects. The maintenance gate must pass before web or worker starts; do not depend on pnpm or repository source inside the running container.
- Only a fresh database or one carrying the exact current packaged ledger is supported. Any other populated or ambiguous state fails closed without adoption or repair. A disposable database may be manually discarded only with the app and every writer stopped and after confirming it contains no valuable user or application data; remove the database, `-wal`, `-shm`, and `-journal` state together. A failed first initialization additionally requires confirmation that no migration completed. Local/manual backups and retained failure artifacts remain operator-controlled and are never deleted automatically; verified R2 routine objects expire through the separately configured 35-day lifecycle after the 30-day lock permits deletion.
- Enable DigitalOcean monitoring, alerts, and backups or an equivalent written backup process.
- Persistent baseline staging/production, and any fork that selects off-host backup, uses a dedicated private Cloudflare R2 bucket separate from durable user Files/media. Follow [the backup runbook](backup-runbook.md): six-hour snapshots, 12-hour freshness incident threshold, 30-day lock, 35-day lifecycle, monthly isolated drill, and no RPO/RTO promise. A fork may omit this capability and document or replace the resulting recovery boundary.
- Configure the exact runtime `NUXT_*` keys from `.env.production.example`, including private `NUXT_READINESS_TOKEN`, exact `NUXT_SOCIAL_PROVIDERS_GOOGLE_ENABLED=true|false`, exact private `NUXT_OPENAI_FILE_SEARCH_ENABLED=true|false` and `NUXT_OPENAI_WEB_SEARCH_ENABLED=true|false`, and one complete SMTP email transport; legacy unprefixed aliases are unsupported. In Coolify, runtime-only values are Runtime-enabled and Build-disabled. If Observability is enabled, make its flag available at build and runtime, supply the Sentry token only as a Docker Build Secret, and supply the non-secret upload controls as build-only arguments. Every `NUXT_MODULES_*_ENABLED` flag is required as lowercase `true` or `false`.
- A false module flag is healthy-disabled and inert across routes, UI, direct services/workers, readiness, and provider calls.
- Build one project-and-commit-scoped image locally through the committed assignment-free `.env.build` and deny-by-default `.dockerignore`. Static generation is unsupported. Local `test:container-build` and `test:container-health` prove secret-shaped root/nested canaries are absent after `COPY` and from image configuration/history and that the final image and maintenance jobs run as non-root. On reviewed Coolify `v4.1.2`, enable Include Source Commit in Build, disable Inject Build Args to Dockerfile, leave Raw Compose Deployment and Consistent Container Names off, keep custom container/internal names blank, and keep custom Compose build/start commands blank so deployment follows the certified build → stop/remove → migrate → same-image start path. Temporarily suspend triggers during manual migration or restore.

## Required Services

- One Git-connected Coolify Compose application with one locally built selected-commit image, web on container port `3000`, and a managed `/app/data` volume.
- One `restart: "no"` migration service that mounts that volume and must complete successfully before any long-lived service starts.
- Exactly one supervised worker running the same selected-commit image as web, with the complete runtime environment and the same local same-host `/app/data` volume. With Jobs enabled it starts through the Sentry preload; with Jobs disabled it skips that preload and remains stable and inert without opening SQLite or initializing application providers. Billing or Files requires Jobs and activates it. Configure init/process supervision, restart after unexpected exit, an application-level and Compose `360s` stop grace, and no inherited web HTTP health check. Process liveness is not a job heartbeat, backlog/deadline, convergence, or readiness claim.
- One private, inert `stripe-sync-runner` uses the same selected-commit image and `/app/data` volume, starts only after migration, and exposes no port or HTTP health check. Only it receives `WCU_STRIPE_MEMBERSHIP_SYNC_KEY`, `WCU_STRIPE_MEMBERSHIP_SYNC_MODE`, and `WCU_MEMBERSHIP_GRANDFATHERED_BEFORE`; every other service explicitly receives empty values. Follow [the synchronization runbook](stripe-membership-sync-runbook.md) for the read-only key boundary, first-run certification, fixed binding, daily schedule, private redacted receipts, freshness alert, and stale-lock recovery.
- Off-host backup is optional for forks and mandatory for persistent baseline staging/production. Enabling it sets `COMPOSE_PROFILES=backup` for build and runtime and creates one private same-image, same-volume, init-backed runner with no port/domain/health check. Only that runner receives non-empty bucket-scoped `BACKUP_R2_*` values and validates them; migration, web, and worker explicitly override Coolify's shared `env_file` values to empty. #36 provisions the real bucket/policies, runner/release topology, private off-host receipt sink, and independently scheduled dead-man monitor; #37 creates and configures the Coolify task/notifications, then executes and certifies provider, failure, silence, freshness, and restore behavior.
- Files-enabled production requires Jobs plus the operational worker so delayed deletion and reconciliation remain recoverable. #32 implements persistent local storage, the exact R2 SDK boundary, five-object cleanup pages beneath the fixed lease, bounded provider pagination/retry, and durable queue recovery. Ordinary cleanup remains due at upload-capability expiry plus one minute. After the singleton storage binding exists, the Files-ready worker runs a throttled SQLite `IMMEDIATE` check before claiming work to maintain one viable full-root `{}` cleanup on a 24-hour safety cadence. Only another viable root deduplicates it, so continuous queue traffic and non-root/cursor jobs cannot suppress the recurring root. Recurring roots cover an R2 PUT that began before presign expiry but completed after the ordinary sweep without assuming a provider completion bound. Worker outage delays physical cleanup. The local adapter deliberately fails closed when one cleanup invocation encounters more than 10,000 filesystem entries; do not grow a local namespace past that ceiling without an approved inventory design and migration. Its file sync plus immutable publication is process-restart evidence, not certification against abrupt host-power-loss or persistent-volume failure; backup/staging evidence must establish the mounted filesystem's durability. Keep R2 disabled in deployed staging/production until #37 certifies the real token scope, endpoint, CORS, browser transfers, provider failures, pagination, and deletion convergence.
- Billing-enabled production also requires Jobs and that worker. A billing owner's fresh exact account-deletion command durably records and synchronously attempts immediate Stripe cancellation without automatic refund/proration, retrieves confirmation, and enters local deletion only after confirmation. Ambiguity retains identity and private state. The worker may retry cancellation/retrieval only and never delete the user; after worker confirmation, the person must submit another fresh exact deletion command. Alert on the oldest due Billing job, pending cancellation age, and missed scheduled-effect deadlines.
- The database persists one exact Files binding: driver and bucket plus the normalized account-and-jurisdiction endpoint for R2. Every later file operation and cleanup run must match it and fail closed before provider mutation or metadata removal on mismatch. Never switch `NUXT_FILES_DRIVER`, replace the R2 bucket, change its account/jurisdiction endpoint, or repoint existing metadata through environment changes alone. No provider-migration command is included; retain the bound identity until a stopped-writer procedure can inventory, copy, verify, cut over, and roll back every stored object deliberately.
- Cloudflare DNS, CDN cache, WAF, R2, and the app's narrowly scoped Turnstile widget for magic-link requests. Use a real hostname-restricted widget in production, never Cloudflare's dummy test credentials. Files and AI do not use Turnstile; Cloudflare is not in the model-call path.
- OpenAI API becomes a production service only when the independently optional AI module is deliberately enabled after #37 certification. Keep nested File and Web Search switches false by default; this requires no vector store/domain policy and adds no tool/provider call. Use an environment-specific project and restricted runtime service-account key, configure project spend/rate limits, and supply private `NUXT_OPENAI_API_KEY`, `NUXT_OPENAI_PROJECT_ID`, and exact `NUXT_OPENAI_MODEL=gpt-5.6-luna`. File Search additionally binds one private vector store for a deployment-owned read-only corpus. Web Search additionally binds one through 100 canonical comma-separated domains. Either enabled tool uses automatic choice and one total built-in call; when both are offered, one turn uses File or Web Search, not both. Raw queries/actions/results are not requested or persisted; File citations retain title only and Web citations retain bounded title/HTTPS URL/source span. `store: false` is not Zero Data Retention; Files/vector stores are persistent provider application state, and live Web Search is not HIPAA/BAA-covered. Use separate corpus-operator credentials only while invoking the bounded prepare/verify/delete workflow; never put them in application runtime. Keep AI/File/Web Search disabled until #37 proves real model/request/error, permissions, corpus and domain behavior, citations/offsets, billing/spend, retention/ZDR/MAM/HIPAA, third-party behavior, deletion, and no-content logging.
- Stripe restricted key and webhook secret, one Product with five distinct Prices (Personal weekly/monthly/annual and Family monthly/annual), the explicit reviewed Portal configuration, and the exact webhook endpoint with only the documented 21 events. Keep all eight `NUXT_STRIPE_*` values Runtime-only and Build-disabled. Configure eight Smart Retry attempts over no more than 14 days; application-owned transitions, pending invitation reservations, manager removal, grace/deadline handling, reconciliation, and cancellation-before-deletion all require durable Jobs processing.
- Stripe membership synchronization uses a different restricted read-only key and makes no Stripe mutation. Its first representative full-account read must establish duration, retained-snapshot growth, required read permissions, denied write permissions, and schedule headroom before daily production execution. It is not a deletion feed and does not infer deletion from a missing provider object.
- Sentry project for server and client visibility.
- Authenticated SMTP provider plus a verified sending identity/domain. Startup/readiness validates its configuration but does not certify delivery; a resolved send proves transport acceptance only, and R-033 owns real magic-link/invitation inbox and provider evidence.
- Google Cloud OAuth web client and consent screen only when Google is enabled. Keep it false until the exact callback and R-033 consent/link/removal/revocation matrix pass; local unlink is not upstream grant revocation.

## Liveness and Readiness

- Public liveness: empty `204` from `GET /api/live`; it does not prove dependency readiness.
- Container readiness: the Dockerfile sends the private Bearer token to container-local `GET /api/ready`, accepts only exact `200` ready output, and exits nonzero on failure. It proves current database/manifest availability, not migration-ledger identity, worker liveness, OpenAI connectivity, vector-store existence, corpus search, retention, or deletion. It makes no provider call and never replaces the pre-start maintenance gate or #37. Coolify gives that Dockerfile check precedence over a UI health check.
- The worker has no HTTP readiness endpoint. Monitor its process exit/restart, graceful shutdown, oldest-due backlog, pending Stripe cancellation age, scheduled-effect deadlines, and safe lifecycle/status logs; inspect fixed bounded diagnostic codes in SQLite when triaging a failed row. Web readiness does not prove worker liveness, restart safety, backlog, deadlines, or cleanup progress.
- Never put `NUXT_READINESS_TOKEN` in a query string, public smoke command, build argument, image layer, or log.
- Non-mutating release smoke check: `pnpm run ops:smoke -- --base-url=https://app.example.com`. It sends credential-free `GET` requests and derives enabled/disabled route expectations from `/api/baseline`; it never receives the readiness token.
- Do not run mutating smoke against production. Use only an approved designated-account read journey after deploy; exercise magic-link account creation with real Turnstile action/hostname validation, invitation send/resend/acceptance, real email delivery, uploads, billing, and webhook delivery in isolated staging with separate provider resources/[sandboxes](https://docs.stripe.com/sandboxes). Files tests do not submit a Turnstile token.
- Review Sentry errors, Coolify logs, and DigitalOcean resource alerts after every production release.
